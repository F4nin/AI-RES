# Группы разработки AI RES

**Дата:** 2026-11-17 · **Статус:** ACCEPTED — рабочий подход принят владельцем; карта групп подготовлена Implementation Lead в рамках поручения. **Решения:** ADR-124, порядок общей реализации/приёмки уточнён владельцем в ADR-127.

Основание: владелец предложил запускать реализацию групп, поручил задокументировать подход для дальнейшей работы и отдельно подтвердил сохранение градации этапов. Документирование не запускает реализацию группы.

## 1. Два уровня плана

**Группа — единица поручения, общей отладки, проверки и доставки. Этап Sxx — единица scope, реализации и traceability.** Номера, scope, зависимости, промпты, DoD, статусы и отчёты S00–S39 сохраняются. Одна группа обычно доставляется одним PR; внутри остаются различимые этапы, их scope и отчёты. Канонические требования и права продукта не меняются.

Одна команда «Реализуй группу G01» разрешает последовательное прохождение перечисленных в ней этапов до общего результата без новой команды на каждый Sxx. Сначала реализуется состав группы в порядке внутренних зависимостей, затем выполняются общая отладка, применимые проверки всех этапов, независимое review и доставка. Отдельные полный pre-pr, CI и PR/merge после каждого внутреннего этапа не требуются. Внешние зависимости должны быть DONE перед соответствующим зависимым Sxx, а не обязательно до старта всей группы; внутренние можно использовать после реализации нужного механизма в той же ветке, сохраняя статус IMPLEMENTED до общей приёмки. Изменение scope группы требует нового решения, технические решения внутри scope — по CHARTER.

Команда «Реализуй следующий пункт согласно плану» по-прежнему разрешает один инкремент по AGENTS §10. Команда на группу активирует групповой режим. Команда без указания группы не разрешает самостоятельно выбрать несколько групп. После завершения группы агент останавливается; следующая группа автоматически не запускается.

## 2. Карта оставшейся разработки

Это группировка оставшихся S17–S39, а не новая нумерация этапов. Порядок в колонке «Состав» — рекомендуемый внутренний порядок исполнения; все точные зависимости дополнительно проверяются по ROADMAP и промптам. Внутри группы работа может остановиться в ожидании результата другой группы. Группа не создаёт зависимости «дождаться всей другой группы», если этапу нужен только один её завершённый этап.

| Группа | Общий результат / принцип объединения | Состав | Внешние зависимости и ограничения |
|---|---|---|---|

| **G02 — Инструменты и планирование Manager** | Контролируемое использование инструментов, intake и формирование плана/задач | S17 → S20 → S21 | S17: S07/S12, ARCH-01 DONE, но SLICE-01 перед S17 сохраняется. S20: S12/S15/**S19**. S21: S20. Реальная модель — только после допуска; тестовый двойник по ADR-022 не доказывает её качество |
| **G03 — Выполнение и независимый QA** | Безопасный цикл Gate → WorkerRun → coordination → QA/rework | S22 → S23 → S24 → S25 | S22: S14/**S17/S18/S19/S21**; S23 дополнительно S15. Перед реальными Run закрываются применимые security/reconciliation/budget gaps; каждый Run проходит актуальный Gate |

| **G06 — Web Workspace** | Пользователь получает интерфейс платформы: от foundation до полного сценария | S35 → S36 | S35: S12, может разрабатываться раньше backend-групп. S36: S35/**S31**. Между этапами вероятно ожидание; не закрывать отсутствующие backend-сценарии моками |

S33: S32/S16 + OD-01/OD-02 и допуск профиля. S34: S33 и применимые model gates. Backup/restore — в scope S32; ранее отдельно отложенные сценарии не возобновляются до соответствующего поручения |
| **G08 — Итоговая проверка и приёмка** | Подтверждены безопасность, производительность, UX и эксплуатационная готовность | S37 → S38 → S39 | S37: **S32/S36**/S16 и real-provider/security acceptance. S38: S37 + OD-02. S39: S37/S36 + UI acceptance владельца. S38/S39 независимы друг от друга; release/deployment не разрешаются автоматически |

Принцип: объединять соседние по продуктовому результату работы и сохранять точки проверки. Группы не делятся только по слоям «весь backend / все тесты / вся документация»: тесты, безопасность, observability и документация сопровождают код каждого этапа, а общий прогон и отладка проводятся по готовому составу группы.

### Завершённые этапы и мини-этапы

S00–S16 остаются в исходном roadmap с существующими статусами и evidence. Они не включаются в новые группы для повторной реализации. S16 DONE означает технический milestone по ADR-123, а не допуск реального профиля.

CI-01, ARCH-01 и DEP-01 не переоткрываются. SLICE-01, PROF-01, принятые приоритеты мини-этапов и ещё не оформленная работа по архивации/лёгким отчётам остаются в существующем контуре ROADMAP/ADR-115/116/HANDOFF. Их не считать выполненными и не поглощать группами молча. В частности, SLICE-01 остаётся перед S17; для него нужны допущенный реальный профиль и свои условия расходов. Независимые группы выбираются явным поручением владельца, а не обходом этого барьера внутри G02.

## 3. Как запускать группу

Пример поручения: «Продолжаем разработку AI RES. Реализуй группу G01 по DEVELOPMENT_GROUPS.md. Сохрани этапы и их проверки. Пройди группу до завершения или блокера». Это пример будущей команды, не действующее поручение на G01.

1. Прочитать полный AGENTS, CONTEXT_RETENTION, обязательные источники и этот документ. Восстановить Git, текущую работу, owner decisions и evidence. Уже завершённые этапы пропустить с указанием evidence; незавершённый этап выбранной группы сначала продолжить.
2. Создать паспорт выбранной группы в `groups/Gxx_WORK.md` по [шаблону](tooling/GROUP_WORK_TEMPLATE.md). Зафиксировать точный scope, внутренний порядок, источники, зависимости, ветку/базовый SHA, затрагиваемые файлы, gates, права и внешние блокеры. Паспорт не может расширить исходное поручение.
3. Проверить DONE внешних зависимостей очередного зависимого Sxx, owner-блокеры, источники и среду. Внешняя предпосылка будущего этапа не блокирует независимую раннюю часть группы (например, S35 до готовности S31 для S36). В паспорте отделить внутренние зависимости этой группы: сохранить их порядок и реализовать необходимый контракт перед зависимым кодом в той же ветке. Внешнее обещание соседнего окна или незавершённый этап другой группы не является DONE.
4. Реализовать все порученные Sxx вместе с их тестами, миграциями, observability и черновиками отчётов. Держать логические checkpoints и контролировать diff; отдельный полный pre-pr/CI/review/PR/merge между этапами не обязателен. При конкретной пользе выполнять точечные проверки; отсутствие промежуточного прогона не является блокером само по себе.
5. После реализации состава выполнить общую отладку и все применимые gates входящих этапов по объединённому diff: локальные suites, полный pre-pr, независимое review с требуемыми компетенциями и исправления. Общий прогон/review может покрывать несколько Sxx; явно связать каждый этап с cases, SHA, результатами и limitations. После изменений повторить затронутые проверки.
6. Доставить группу одним PR и проверить обязательный Linux CI и дополнительные security/supply-chain jobs по точному финальному SHA перед merge. Не требовать отдельного PR каждого Sxx. VERIFIED/DONE присваивать только этапам с доказанными применимыми DoD; общий зелёный статус без coverage их scope недостаточен. После merge проверить Git/CI и сохранить evidence.
7. При внешнем блокере сохранить фазу группы, статус каждого Sxx и точную оставшуюся работу. Остановить затронутую часть; не обходить owner/security/product gates и не выбирать другую группу. При завершении дать групповой отчёт со ссылками на Sxx reports/reviews/общий PR/CI; остановиться до новой команды. Уже доставленные этапы повторно не реализуются.

### Статус группы

Паспорт использует плановые статусы `NOT_STARTED`, `IN_PROGRESS`, `BLOCKED`, `DONE`. Они не заменяют статусы реализации Sxx. Группа DONE только если все её этапы DONE по ADR-032 и применимым явным owner-уточнениям, общий результат проверен, evidence/контекст сохранены. Частично завершённая группа остаётся IN_PROGRESS или BLOCKED; таблица этапов показывает фактический прогресс. Уже принятые owner-исключения не переносятся автоматически на другие этапы.

## 4. Несколько терминалов

Групповой режим полезен и в одном терминале: сокращает число ручных поручений. Параллельный запуск — дополнительный режим по явному поручению на несколько названных групп, после проверки независимости текущих этапов. Работа группы не означает, что все её этапы независимы от соседней группы.

Исторически до поручения G01 для первой параллельной волны были предложены **G01 и G06**, два исполнителя и координатор. G01 готовит контекст/правила, G06 начинает S35; S36 ожидает S31. Это рекомендация, не запуск пилота и не обещание завершить обе группы одновременно. Следующая возможная ветвь — G04 после проверки ограничений S27; G02 ждёт сохранённых условий SLICE-01. Число одновременных исполнителей увеличивается только по результатам пилота и доступности ресурсов.

### Какие группы можно запускать параллельно

Исторический снимок до выполнения G01, 2026-11-17 (текущие статусы сверять отдельно, DONE не переоткрывать): G01 можно было начать по выполненным предпосылкам S18/S19; G06 — с S35, затем ожидать S31; G04 — кандидат после проверки ограничений S27 по embeddings/реальной orchestration. G02 пока ждёт SLICE-01 перед S17. G03/G05/G07/G08 пока не имеют выполненных предпосылок первого этапа. READY в индексе не заменяет проверку блокеров и поручение на конкретную группу.

| Когда выполнены предпосылки | Возможное параллельное сочетание | Точки ожидания |
|---|---|---|
| На исходном checkpoint до поручения G01 | **G01 + G06** | G01 проходит S19/S18; G06 начинает S35, но S36 ждёт S31 из G05 |
| Проверены ограничения S27, доступен безопасный scope и ресурсы | **G01/G06 + G04** как дополнительный поток | В G04 S28 ждёт S19, S29 — S17; embeddings и реальная orchestration требуют своих допусков. Это условный вариант, а не безусловная готовность всей G04 |
| Завершены G01 и условия SLICE-01, есть поручения на группы | **G02 + G04**, если G04 ещё не завершена | G02 проходит S17/S20/S21; G04 может ожидать S17 для S29. Применимые блокеры S27 сохраняются |
| Готовы все предпосылки S22 | **G03 + оставшаяся работа G04** | G03 проходит S22–S25; G05 позднее требует S25 и результаты знаний S28/S29 |
| Завершён S31 из G05, S35 уже DONE | **Продолжение G06 + G07** | S36 и S32 не зависят друг от друга; S33/S34 сохраняют model/evaluation/owner gates |

Это карта возможностей, не обязательные пакетные барьеры: завершённые этапы не повторяются, каждая предпосылка проверяется отдельно. Первая строка не означает, что обе группы можно довести до DONE без результатов остальных групп. G08 начинается после своих точных предпосылок S32/S36/S16 и применимых model/security gates; ждать всей G07 только ради групповой границы не требуется. После остановки на внешней зависимости продолжение группы требует команды по §3. Параллельность реализации не разрешает одновременные операции над общим runtime.

Правила изоляции и координации:

- Каждое окно-исполнитель получает свой Git worktree, ветку порученной группы, паспорт и ограниченный scope. Два агента не пишут в одну рабочую копию. Запуск процессов из одного каталога не является изоляцией.
- Координатор владеет распределением общих файлов, integration/merge-порядком и общим контекстом. Исполнители ведут свои паспорта и stage reports; координатор объединяет изменения STATUS/HANDOFF/ADL/ECC/traceability и индекса без потери записей соседей. Владение — на конкретный этап/волну, с передачей при необходимости.
- До параллельных правок распределить API wiring, `contracts/`, миграции/Alembic head, `Makefile`, CI, manifest/lock-файлы и общие документы. При пересечении назначить одного автора и согласовать очередность. Разные модули могут менять одни и те же общие файлы.
- Существующие ADR-номера резервирует координатор; одновременная выдача одного номера запрещена. Изменения миграций интегрируются согласованно, без незамеченных нескольких heads и без переписывания immutable revisions.
- Внешняя предпосылка другого потока должна быть DONE и доставлена. Внутри одной порученной группы достаточно реализованного нужного контракта в её ветке, с последующей общей приёмкой. После изменения интегрированной базы повторяются затронутые проверки и обязательный CI точного SHA; старый PASS не относится к новому diff.
- Scope каждого этапа должен быть покрыт независимым review; общий отчёт review группы допустим с явным покрытием Sxx и нужных компетенций. Автор не выступает независимым reviewer своего кода; перекрёстная проверка соседней группы допустима только без авторства проверяемого среза и с blind-first, профильными компетенциями и evidence.
- Зависимости, egress, budgets и approvals остаются в прежних точных границах. Общая команда на группы не выдаёт новый бюджет и не принимает WORKING-параметры.

### Ограничение текущего runtime

Исследование текущего кода выявило общие ресурсы: `infra/compose.yaml` содержит `name: ai-res`, фиксированную подсеть `172.28.20.0/24`, адрес proxy, host-порт `8443`, named volumes и общие локальные теги вроде `ai-res/api:dev`. `Makefile` запускает `up --build --remove-orphans`; полный `pre-pr` включает поднятие основного и PoC-стека. Другой терминал может заменить образ, контейнеры или окружение выполняемой проверки.

Поэтому первый режим — **параллельная реализация и безопасные локальные проверки, последовательное использование общего runtime под управлением координатора**. Worktree и отдельный `COMPOSE_PROJECT_NAME` сами по себе не изолируют сети, порты, образы и данные.

Перед тяжёлым прогоном координатор фиксирует владельца runtime, checkout/SHA/diff, миграционное состояние, совместимость существующих данных и границы команд. Другие окна не запускают операции над этой средой. Одной очереди команд недостаточно, если БД уже содержит несовместимые миграции другой ветки: нужен проверенный совместимый путь либо отдельная чистая тестовая среда штатными механизмами. Удаление существующих volumes/данных для переключения запрещено без отдельного решения. Если безопасного пути нет, runtime-проверка блокируется, а не засчитывается по чужому стеку.

Одновременные полные стеки требуют отдельно подготовленной и проверенной изоляции портов, сетей, образов, volumes, secrets и test endpoints либо отдельных Docker-сред. Такое tooling-изменение не реализовано этим документом. Безопасность существующего dev-стека и обязательные gates сохраняются.

## 5. Что даёт подход и как оценить результат

Ожидаемая польза — меньше ручных запусков, непрерывное прохождение согласованного scope и возможность перекрывать независимую работу. Количество необходимых продуктовых проверок не уменьшается. Ускорение не измерено; число окон не равно коэффициенту ускорения, последовательный путь S22–S25 и точки схождения остаются.

В пилоте сохранить время работы/ожидания по этапам, ручные вмешательства владельца, конфликты общих файлов, повторные проверки после интеграции, ожидание runtime и findings review. Сравнивать с имеющимся evidence сопоставимых этапов, без выдуманного процента ускорения. Основания для пересмотра границ групп — длительное ожидание внешней зависимости, частые конфликты или слишком большой непроверенный diff; scope Sxx изменяется только отдельным согласованным решением.
