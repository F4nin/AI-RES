# CI-01 — Ускорение CI и локального прогона тестов (мини-этап вне нумерации S)

**Фаза:** вне фаз (инструментальный мини-этап, ADR-112) · **Соответствие Spec:** — (S03 «CI baseline» остаётся нормативным; этап не меняет Definition of Done) · **Roadmap:** вне последовательности S00–S39

> **СТАТУС ПРОМПТА: READY.** Зависимостей нет: S15 VERIFIED и влит в `main`. Не блокирует S16 и не меняет его скоуп. Ветка: `ci/ci-01-faster-pipeline` (поверх `docs/od01-profiles-adr-111`).

## 1. Роль и границы

Ты — Principal Architect и Implementation Lead проекта AI RES. Этап инструментальный: он ускоряет получение доказательств, но **не ослабляет их**. Если ускорение требует убрать, пропустить или ослабить проверку — не делай этого и запиши как отклонённую альтернативу.

**Границы (нарушать запрещено):**
- Linux CI на GitHub Actions остаётся финальным доказательством (CLAUDE.md §7, `make pre-pr`).
- Набор проверок не уменьшается: те же 1286 backend-тестов (имена не пропадают), infra 307, runtime 148, contracts 22, import-linter 12 kept, hadolint, actionlint, scan секретов, SBOM + скан уязвимостей (own images blocking), `infra-verify-digests`.
- Нет `latest`, нет непривязанных образов и actions: actions закреплены по SHA, образы по digest; новые версии — не младше двух недель.
- Нет новых сервисов в топологии, нет внешних сервисов кеша/отчётов, которые получают код или данные проекта (ecc-precedence: не отправлять код во внешние сервисы без согласия владельца). Кеш GitHub Actions — допустим.
- Секреты не появляются в логах, кешах и артефактах CI.
- SQLite не заменяет PostgreSQL (ADR-003); Temporal time-skipping stub не заменяет реальный dev server.
- Нормативные документы `docs/architecture/` и Registry не менять.

## 4. Порядок работ (строго по шагам; каждый шаг — отдельный коммит с измерением до/после)

**Шаг 0 — профиль (без изменений поведения). ВЫПОЛНЕН 2026-11-14.** Результат: миграция на каждый тест — 74% времени выборки (см. таблицу базовой линии и отчёт). Исходная формулировка: объяснить время, не отнесённое к фазам. Метки времени по фазам фикстур (`pg` старт контейнера, `reset_database`, `provision`, `alembic upgrade`, создание движков/event loop, teardown) или `py-spy`. Результат — таблица «где уходит время» в отчёте. Шаги 4–5 стартуют только после него.

**Шаг 1 — зависимости джобов.** Убрать `needs: [backend, infra-static]` у `infra-runtime`; `infra-static` и `backend` остаются независимыми. Проверить, что `infra-runtime` не использует артефакты `backend`. Fail-fast не нужен: джобы независимы и бесплатны (публичный репозиторий).

**Шаг 2 — кеши и разделение тяжёлых шагов.**
- Кеш `uv` через `setup-uv` (`enable-cache`, ключ по `uv.lock`), без кеширования секретов.
- Кеш Docker-слоёв/образов, где это безопасно и не обходит проверку digest.
- SBOM + скан уязвимостей (≈ 298 с) вынести в отдельный параллельный джоб; он остаётся **блокирующим** и использует те же образы.
- Таймаут на каждый джоб; `--durations=30` в выводе pytest в CI (видимость регрессий скорости).

**Шаг 3 — фильтр путей.** `paths-ignore` для изменений только в документации — **после** проверки, какие джобы читают `docs/` (например, `check_prompts.py`, manifest-проверки): если такие проверки есть, вынести их в отдельный лёгкий workflow, который идёт всегда. `main` сейчас не защищена; если появится обязательная проверка, пропущенный workflow заблокирует merge — зафиксировать в отчёте.

**Шаг 4 — готовая схема вместо миграции на каждый тест** (по результатам шага 0). Шаблонная БД (`CREATE DATABASE … TEMPLATE …`) или иной способ: схема мигрируется один раз за сессию из пустой БД через `alembic upgrade head`; тесты, которые проверяют сам upgrade/ревизии (`test_migrations`, `test_migration_safety`, `test_schema_drift` и аналогичные), остаются на пустой БД. Запрещено: подменять реальные миграции снимком SQL, копировать схему вручную, делить состояние между тестами без сброса.

**Шаг 5 — параллельность (`pytest-xdist`).** Только после шага 4. Один контейнер PostgreSQL на воркер (роли общие на весь кластер); число воркеров конфигурируемо; на CI — по числу ядер раннера. Тесты с общим глобальным состоянием помечаются и выполняются последовательно либо изолируются. Порядок и детерминизм: прогон `-p no:randomly`-эквивалент и повторный прогон на каждом шаге.

**Шаг 6 — локальный быстрый путь для разработки с Claude Code.** Цель `make pre-push-fast` (lint + mypy + import-linter + `backend-test-unit` + contracts) как обязательный быстрый слой перед полным `pre-pr`; описать в `docs/implementation/tooling/README.md`. Полный `make pre-pr` остаётся обязательным перед заявлением VERIFIED.

## 5. Не входит

- Изменение состава проверок, DoD, quality gates, нормативных документов.
- Переход на другой CI-провайдер, self-hosted раннеры, платные сервисы, внешние кеши с кодом.
- Оптимизация самого продуктового кода, кроме тестовой инфраструктуры.
- Удаление, отключение или пометка `skip` существующих тестов ради скорости.

## 8. ECC: агенты, skills, commands

| Тип | Имя | Назначение на этапе |
|---|---|---|
| agent | `planner` | декомпозиция шагов и порядка |
| agent | `database-reviewer` | **обязателен для шага 4** (шаблонная БД, роли, RLS-изоляция, сброс состояния) |
| agent | `silent-failure-hunter` | **обязателен для шагов 4–5**: ложные «зелёные» из-за общего состояния, проглоченных ошибок фикстур |

Причина обязательного review (ecc-precedence, п.2): изменение тестовых фикстур, на которых держатся доказательства RLS, ролей и tenant-изоляции; ошибка даёт ложный зелёный результат. Review слепое (агент не читает отчёт автора), находки CRITICAL/HIGH исправляются до VERIFIED. Шаги 1–3 и 6 — конфигурационные; отдельное review не требуется, причина записывается в отчёт.

## 9. Обязательные проверки (acceptance)

- **Эквивалентность набора:** число собранных тестов и список их id до и после совпадают (`pytest --collect-only -q`), отличия — только добавленные тесты этапа.
- **Не слабее доказательств:** все пункты CI acceptance gates для persistence (раздел 3) зелёные, включая upgrade from empty и from previous revision.
- **Негативная проверка фикстуры (шаг 4):** намеренно сломанный шаблон/миграция приводит к красному прогону; тест, зависящий от чистой БД, не видит данных предыдущего теста; tenant A не виден под credentials tenant B.
- **Параллельность (шаг 5):** три подряд прогона с разным числом воркеров дают одинаковый набор passed; нет зависимости от порядка.
- **Fail-closed CI:** `infra-runtime` без стека падает, а не пропускается (`AI_RES_REQUIRE_STACK=1` сохранён); джоб скана уязвимостей остаётся обязательным.
- **Фильтр путей (шаг 3):** коммит только с `docs/**` не запускает полный CI, но проверки, читающие docs, всё равно выполняются; коммит, меняющий код или `.github/**`, запускает полный CI.
- **Воспроизводимость:** итоговый `make pre-pr` локально — exit 0; Linux CI зелёный на финальном коммите (ссылки на run id).

- Все шаги 0–6 выполнены или явно отклонены с обоснованием и измерением.

- Документы и статусы обновлены; отчёт заполнен. Если runtime-проверка невозможна — статус не выше IMPLEMENTED и пометка `IMPLEMENTATION NOT VERIFIED`.
