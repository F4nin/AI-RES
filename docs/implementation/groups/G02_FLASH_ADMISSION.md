## 1. Точная граница

Цепочка входа: G-156 (код и evidence допуска Flash/Bifrost + человеческая приёмка) → SLICE-01 с собственными условиями → S17 → S20 → S21. До первого producer S20 дополнительно ADR129 enforcement + G107. SLICE-01 — инструмент разработки через LLMGatewayPort, а не продуктовый WorkerRun; он не обходит будущий Readiness Gate.

Существующий код: `llm/registry.py` требует pin; `llm/types.py` содержит pinned ModelIdentity; `llm/adapters/bifrost.py` отказывает rolling DeepSeek aliases; `llm/factory.py` предоставляет только unconfigured/test gateway; migration0017 immutable и не переписывается. Эти guards не являются дефектом, который можно убрать одной allowlist-правкой. Нужны отдельная observed identity, admission и durable drift block. Конфигурационный model string не является наблюдением provider.

Разрешено сейчас: спроектировать и реализовывать отключённые contracts/validator/tests и затем durable admission; подготовить оплачиваемый candidate PoC в уже разрешённом общем лимите. Не включать продуктовый профиль, не подделывать APPROVED/immutable evidence, не вызывать Pro/fallback и не расходовать средства SLICE-01.

## 2. Контракт наблюдаемой identity — выбор по делегированию владельца

Первый срез содержит внутренний versioned contract наблюдения и сравнение с явно переданным expected identity. **Выбор состава делегирован владельцем и принят Implementation Lead в ADR131:** fingerprint VALUE обязателен для expectation. Контракт остаётся WORKING implementation-owned; точные реальные значения/evidence и approval профиля ещё требуют отдельной человеческой приёмки. Он не публичный DTO и не утверждение профиля. Активный машинный источник — `contracts/internal/llm-observed-identity.v0.2.schema.json`; чистая реализация — `backend/src/ai_res/llm/observed_identity.py`. Историческая schema0.1 сохранена без изменения; активный parser её отвергает, silent conversion/compatibility bypass нет. Product consumers и сохранённые записи отсутствуют; DB migration не нужна для этого отключённого изменения.

Обязательные факты: точный request model из trusted composition, фактические provider/model/routing model из ответа Bifrost, время наблюдения от trusted clock, безопасные application/provider request references. Только `deepseek` / `deepseek-flash`; returned model сравнивается с точным явно принятым значением, не с wildcard. Локальные code/profile/config/prompt/tool версии фиксируются отдельно; никакое поле не заполняет фиктивный pinned_model_version.

Fingerprint — наблюдаемая metadata с обязательным непустым безопасным VALUE для Flash expectation. В candidate observation отсутствие, явный null и строка представлены явно; incomplete candidate metadata не превращается в допустимый baseline. ABSENT/NULL expectation отвергаются schema, parser и прямым DTO constructor. Вызов с отсутствующим/null/изменившимся fingerprint относительно expected VALUE не проходит сравнение. Это сохраняет доступный сигнал drift для контролируемой инженерии требований. Fingerprint не selector/immutable pin и не approval. Реальные значения и evidence проходят человеческую приёмку **до включения**, как требует DOC076 §3.1; выбор состава теперь закрыт делегированием. Наблюдения candidate PoC — evidence, не принятые продуктовые результаты. Сохранение fingerprint доказано для отдельного patched candidate на fake upstream; official image сохраняет известный defect, real provider ещё не проверен. При отсутствии обязательной metadata допуск закрыт, фиктивное значение или silent relaxation запрещены.

Unknown version/field/type, duplicate JSON keys, malformed/oversized references, неверный UTC timestamp, другой provider/model, fallback/key alias и неверная routing identity → controlled refusal без вывода входных значений. Parser/comparison не имеют функции approve, I/O или власти над бюджетом. Тестовые fixtures синтетические.

JSON Schema задаёт структурный слой; semantic parser дополнительно проверяет исходную JSON-сериализацию: duplicate keys/bytes/размер, строгое integer-представление (1.0 отвергается), secret-shaped references. Перед использованием evidence проходят **обе** проверки, одной schema validation недостаточно. Provider request reference обязателен и nonnull. Незнакомый returned model можно сохранить как candidate observation metadata; expectation ограничен Flash и затем сравнивается по точному значению, не regex. Regex scope gate сам по себе не доказательство модели/approval.

## 3. Реализация после чистого validator

1. Версионировать полное profile/admission/evidence binding до persistence/handlers: immutable mode сохраняется; observed mode ограничен Flash. Отдельно управляемые версии AI RES, факты наблюдения, точная accepted identity и ссылка на человеческое решение. Existing0017 не меняется; compatibility cases обязательны.
2. Backend-owned admission store в ai_res_db: immutable evidence generations, authoritative active generation и sticky blocked state. Новая forward Alembic revision, узкие grants/RLS по canonical access model; Runtime без DB credentials. Audit approval/block обязателен; metadata-only telemetry после redaction.
3. Preflight каждого запроса берёт текущую admission generation; I/O выполняется вне DB transaction. Перед принятием результата — final revalidation под lock/CAS: exact identity, active generation и актуальные права. Drift атомарно блокирует admission и пишет audit до отказа; уже летящие запросы на прежней generation также не принимаются. Reapproval — новый immutable evidence/generation человеком; старые результаты/approval не переписываются. Store/audit outage → fail-closed. После рестарта block сохраняется.
4. Streaming не отдаёт частичный вывод как принятый результат: metadata каждого chunk и итоговое состояние сверяются; tool calls не исполняются до финальной приёмки. Нужны tests drift в начале/середине/конце, missing DONE/usage, concurrency/block/reapproval и lost response.
5. Отдельный trusted candidate probe path не создаёт фиктивный APPROVED profile, не ослабляет обычный gateway и не публикуется как универсальный endpoint. Он ограничен фиксированным Flash/Bifrost route, синтетическими данными, budget reservation и evidence-only output. Key доступен только relay, не Runtime/Bifrost/client/argv/env/logs.
6. После offline checks — реальные candidate calls по §4, independent reviews, исправления, применимые gates и представление владельцу конкретных metadata/evidence/Bifrost/profile для отдельной приёмки. Словарь classification/egress уточнить перед включением; месячный WORKING бюджет не использовать вместо технического лимита.

## 4. Минимальный план реального технического прогона

Официальные источники проверены 2026-11-17: [модели и цены](https://api-docs.deepseek.com/quick_start/pricing/), [Chat Completions](https://api-docs.deepseek.com/api/create-chat-completion/). ID — `deepseek-flash`, опубликованная текущая версия — `DeepSeek-V4.1-Flash-1017`; она не immutable selector. Для верхней оценки берутся peak/cache-miss ставки **0.30 USD / 1M input** и **1.20 USD / 1M output**; скидки и cache-hit заранее не учитываются. Перед самим запуском проверить цены повторно, остановиться при изменении условий.

| Реальный вызов | Проверяемое свойство | Лимит |
|---|---|---|
| 1 | Короткий text response; identity/usage/request reference через Bifrost | 256 output tokens |
| 2 | JSON output + локальная валидация схемы | 256 |
| 3 | Один synthetic function call, без исполнения инструмента | 256 |
| 4 | Полный SSE, identity/usage/DONE | 256 |
| 5 | Отмена SSE, закрытие соединения и учёт возможного списания | 256 |
| 6 | Короткий client timeout, unknown billing и остановка/учёт | 256 |
| 7–8 | Только адресная замена failed/not-observed проверки; без автоматического повторения при неизвестном исходе | 256 на попытку |

Это максимальный конверт **8 HTTP inference attempts суммарно**, не восемь плюс retries. Concurrency1; retries/fallback0 в Bifrost/relay/клиенте; non-thinking; только короткий синтетический текст и function schema, тело ≤4096 UTF-8 bytes. Реальные bad-key/rate-limit/provider outage/security attacks не провоцировать платными запросами, если нужное свойство проверяется локально. Проверки через fake provider не считать реальными provider evidence. Неподдерживаемый JSON schema mode не маскировать success: зафиксировать capability limitation, adapter/schema validation исправить в scope; approval остаётся закрытым.

Рабочая оценка **при предположении** input≤4096 tokens: одна попытка ≤0.001536 USD, восемь ≤0.012288 USD. Это расчёт, не измеренный usage и не hard token bound из числа bytes. Строгая консервативная резервация использует **2,000,000 input tokens на попытку**, что с запасом покрывает опубликованный 1M context (включая decimal/binary трактовку); 256 output. Верхняя стоимость попытки **0.6003072 USD**, всего **4.8024576 USD**. Указанное большое число — только резерв для расчёта; payload/context не увеличивать до него. Расчёт выполнен Decimal; провайдеру такой max_input параметр не приписывается.

Общий ранее утверждённый потолок — **10 USD** на этот технический прогон, включая старый S16 лимит; историческое model spend0, нового кошелька нет. До dispatch durable cumulative ledger резервирует полную верхнюю стоимость **каждой** попытки атомарно. При lost reply/timeout/cancel/ошибке без достоверного usage полный резерв остаётся занятым; retry требует нового резерва и места в тех же восьми попытках. Restart/новый процесс не обнуляют счётчик. Остаток =10 − settled − reserved/unknown, без двойного списания после reconciliation. Missing/outdated tariffs, ledger/audit failure, необъяснимое расхождение billing, недостаточный остаток или исчерпание8attempts → остановка. Пока ledger/probe не реализованы и ключ не подключён, **вызовы не выполнять**.

После запуска отчёт: attempts по кейсам, tokens/input cache, settled estimate по тарифам, unavailable usage/unknown reserve, provider balance/billing evidence отдельно, фактические retries, remaining ceiling. Нулевая/неполная телеметрия не доказывает нулевой счёт. Prompt/response contents/ключи не включать в отчёт; capability/assertion summaries и безопасные metadata достаточны. SLICE-01 и месячная эксплуатация в этот план не входят.

## 5. Приёмка, ECC и остановка

Текущий validator проверяют настоящие unit/contract tests; product gateway остаётся закрытым. Следующий durable срез проверяют на PostgreSQL16: empty/previous upgrade, drift0, grants/RLS/tenant reset, concurrent begin/finalize/block/reapproval, рестарт и audit/store failure. Дополнительно no fallback, no automatic approval, данные/секреты не попадают в вывод/telemetry. Реальные provider capability/usage/isolation tests по DOC076 §7 остаются до допуска. Полный pre-pr и Linux CI итогового product diff обязательны; узкий offline PASS не даёт VERIFIED модели.

ECC: planner/architect — цепочка зависимостей и контракт; python-patterns/python-testing/tdd-workflow/contract-first — реальный validator/tests; независимые code/security reviewers — parsing/failure semantics и границы admission. Для persistence добавить database-reviewer; для транспорта/stream — silent-failure-hunter и test analyzer. Native Claude commands/hooks не объявляются запущенными.

Вопросы владельцу обсуждаются по одному. Состав metadata выбран по делегированию владельца в ADR131, повторного вопроса optional/mandatory нет. До включения обязательна отдельная человеческая приёмка точных реальных значений/evidence и Bifrost/profile; она не выполнена. Ключ подключать только через существующий SOPS/age → Compose secrets, после отдельной конкретизации безопасного setup; значение не передавать в чат. Расходы уже разрешены в точном потолке, повторное разрешение на те же расходы не запрашивается. Подключение ключа не отменяет недоделанный ledger/probe или допуск. При блокере сохранить фактическую фазу G02/G156 и не переходить в S17/S20.

## 6. Следующий candidate egress seam: ограниченный технический план

**Исторический read-only план до ADR134; сейчас control/relay локально TESTED, полный live security/runtime acceptance NOT VERIFIED.** Независимый read-only security/architect analysis рекомендует A: relay → narrow private-TLS backend claim непосредственно перед provider send. Альтернатива B (подписанный offline permit с boot nonce/replay cache) требует нового криптографического wire protocol и оставляет интервал устаревшей авторизации; для этого узкого PoC дополнительная сложность не нужна. Существуют ServiceName.LLM_GATEWAY и Ed25519 service identities, на момент плана endpoint/capability/TLS wiring отсутствовали, теперь реализованы в отдельной candidate app; ADR129 product enforcement этим не закрывается.

- После Bifrost relay строго проверяет versioned payload, формирует canonical окончательные bytes, считает digest и после claim отправляет ровно эти bytes через content=; последующий json=payload запрещён как нарушение binding.
- Backend выбирает единственный technical account/plan сервером; only LLM_GATEWAY capability, private CA/hostname verification, no public router/plaintext path/client-selected account/grants. Relay не получает DB credentials. Static Bearer/allowbool без успешного onceclaim не дают egress.
- Digest должен совпадать с заранее reserved синтетическим case. Claim+audit commit до positive reply; store/audit/TLS/auth/timeout/malformed response → no send. Claim response lost не превращается в идемпотентный dispatch retry.
- Повтор body hash в original account запрещён навсегда, включая settled attempts: иначе старый запрос может consume новую reservation. Каждая попытка/replacement имеет новый synthetic marker внутри хешируемого body, без проектного содержимого/идентификаторов. Ledger draft0024 включает UNIQUE(account_id,body_sha256).
- Unknown outcome сохраняет полный reserve; pending после crash не очищается. Нет auto retry/fallback/refund. Settlement callback должен сохранить metadata-only usage/outcome до признания completion, без secret/raw body logging.
- Перед live нужны real PG concurrency/restart/replay/lost response, private TLS и issuer/audience/capability negatives, реальный pinned Bifrost с fake upstream для доказательства exact post-transform bytes; это ещё не live-provider evidence.

Этот анализ выполнен отдельным g02_scope_security_review read-only: без правок/runtime/modelcalls. Он не является approval будущего кода. После этого анализа root начал endpoint/relay по ADR134; bounded runner ещё впереди. Локально TESTED ADR133 остаётся только ledger foundation.

## 7. Обнаруженная несовместимость Bifrost SSE: read-only предложение исправления

**Первоначальное предложение2026-11-18; теперь technical implementation scope ACCEPTED в [ADR135](../decisions/ADR-135-bifrost-candidate-fingerprint-patch.md), SDK/build/native-fixture локально TESTED; полный G156 NOT VERIFIED.** Runner/control локально TESTED; official image2.5.1 сохраняет первый upstream fingerprint, но synthetic terminal chunk сериализует пустой string; patched candidate теперь локально проверен, original negative сохранён. Strict adapter отказывает. Не считать negative fixture PASS доказательством поддержки SSE. Официальный image/основной stack/S16 не менять молча; DTO/guard ADR131 не ослаблять.

Исследование `g02_prerequisite_plan` по pinned official source commit7cb75fb2f8276ca48d0792c857fecb67b8879e2f: возможная локальная candidate patch затрагивает `core/providers/openai/openai.go`, `core/schemas/chatcompletions.go`, `core/schemas/bifrost.go`. Для exact DeepSeek Flash path читать tri-state fingerprint каждого raw frame **до** decode/continue/suppression; malformed/duplicate/invalid fields или любая смена presence/value дают безопасную ошибку без fallback. A→B→A на suppressed finish/usage тоже запрещается. Каждый forwarded chunk получает собственную фактическую metadata, terminal — последнее проверенное наблюдение; first-value fill запрещён. Existing public string field сохраняется, internal json:- metadata + native stream serialization overlay сохраняют ABSENT/NULL/VALUE и existing WithPreservedUsage/explicit-zero counters. Это предложение, не утверждение корректности такой реализации.

Build trap: официальный transports/Dockerfile копирует только transports и скачивает published core, поэтому patch checkout/core сама в binary не попадёт. Нужна отдельная local-workspace/local-core build с pinned source/toolchain/patch hash, immutable image ID и отдельной candidate tag; без публикации, retag official/main image или deployment. Upstream manifest/lock и license/source provenance требуют проверки перед сборкой.

До выбора/реализации: technical ADR с точным scope. До принятия: Go serialization/stream tests (stable VALUE/NULL/ABSENT+zero usage; drift content/finish/usage, A→B→A, invalid/duplicate, no retry/fallback, upstream close/state isolation), independent Go/security review и actual patched-image positive SSE/negative suite. Существующий official-image negative сохранить. Альтернатива — оставить SSE gate закрытым до проверенного upstream fix. Ни вариант не утверждает реальную модель и не закрывает G156/SLICE/G02.
