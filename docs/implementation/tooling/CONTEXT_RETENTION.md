# Сохранение контекста и продолжение разработки

**Обновлено:** 2026-11-17. Постоянный порядок и разрешения владельца — [AGENTS.md §10](../../../AGENTS.md#10-разработка-одного-инкремента-по-короткой-команде); запись решения — [DECISIONS_PENDING.md](../DECISIONS_PENDING.md#постоянный-процесс-разработки-codex--решение-владельца-2026-11-17). Этот документ развивает существующий механизм handoff (ADR-040), не создаёт новую очередь задач.

## 1. Начало или возобновление сессии

Короткая команда «Продолжаем разработку AI-RES. Реализуй следующий пункт согласно плану» разрешает один инкремент по AGENTS.md §10. Запрос обсуждения или аудита сам по себе реализацию не запускает.

1. Явно прочитать применимые AGENTS.md, CLAUDE.md, Registry и стартовые документы по AGENTS.md §2, включая CHARTER, ROADMAP, HANDOFF, STATUS, индекс промптов и tooling README. Проверить наличие canonical файлов; исторические ссылки разрешать через Registry. Затем прочитать scope выбранного этапа, его источники, ADR, gaps, решения владельца, quality gates и тестовую стратегию.
2. Установить рабочую ветку, HEAD, `git status --short`, diff и историю. Не считать локальные refs свежими без проверки. Сопоставить отчёты, code/tests/migrations, review и CI evidence с проверенными версиями. Наличие файла или DONE в таблице не заменяет evidence.
3. Сначала продолжить начатый незавершённый инкремент: реализацию, исправления review, оставшиеся проверки либо CI/доставку. Не создавать второй инкремент поверх него. Если текущий инкремент BLOCKED, не обходить его без решения владельца.
4. Если текущая работа закрыта, определить следующий пункт по ROADMAP и действующим owner/ADR решениям о мини-этапах. Не ограничиваться номером S и не брать произвольный READY. Проверить зависимости, блокеры и принятый приоритет. При нескольких вариантах без приоритета представить владельцу варианты. Устаревшие строки сверять по порядку «Устаревшие инструкции» в DECISIONS_PENDING, а не по дате файла.
5. Для мини-этапа, чей промпт по принятому решению пишется при старте, подготовить его в существующей структуре из согласованного scope. Отсутствие заранее написанного промпта не разрешает изобретать требования. При нехватке утверждённого scope запросить решение.
6. Проверить нужные архитектурные, программные, инфраструктурные и инструментальные зависимости; обозначить scope и составить план. Разрешённые восстановления зависимостей, dev/test-действия и временные MCP — AGENTS.md §10. Не восстанавливать инструменты без необходимости и не выводить секреты.

`session-brief` остаётся механизмом Claude Code; Codex читает файлы явно. MEMORY.md, Claude slash commands, hooks и память чата не являются обязательным источником восстановления. Не создавать глобальную память или hooks как часть этого процесса.

## 2. Выполнение и проверки

Инженерный цикл, review и доставка — AGENTS.md §7/§10, QUALITY_GATES и промпт этапа. Подбирать полезные компетенции ECC во всём цикле; фиксировать способ применения. Обязательное независимое review — отдельными read-only проверяющими, blind-first, с evidence. При его недоступности статус не выше TESTED, merge запрещён.

Команды брать из прочитанных Makefile/CI: быстрый слой `make pre-push-fast`, далее применимые contracts/backend/infra проверки; полный `make pre-pr` перед VERIFIED продуктового этапа. Он поднимает локальный dev-стек, может подготовить недостающие секреты и применить миграции. Это охвачено разрешением на инкремент при проверенном dev/test назначении среды. Удаление volumes/сброс данных, разрушительные миграции, ротация существующих секретов и production-действия отдельного разрешения не получили.

После review и локальных проверок commit/push/PR/merge выполняются без повторного вопроса в согласованном scope; merge — после обязательного Linux CI и остальных gates. Проверять оба workflow и дополнительные jobs, точный SHA, counts/skips, ссылки. Любые исправления остаются в том же инкременте. Git-доставка не означает автоматического approval профиля модели, требований, Baseline или релиза.

Для узких документационных задач обосновывать неприменимость runtime/migration/API gates; детерминированная проверка документов и review не объявляются runtime verification продукта. Изменения обязательных gates этим документом не вводятся.

## 3. Сохранение при завершении или остановке

В разрешённом scope автоматически обновить контекст после завершения, при блокировке, паузе и передаче работы следующей сессии; перед compaction — когда граница известна и есть возможность записи. Не полагаться на получение автоматического уведомления о завершении сессии.

В начале CONTEXT_HANDOFF разместить краткую актуальную сводку со ссылками на подробности. Ориентир 60 строк относится к сводке для прежнего Claude hook, а не к обязательному удалению истории; существующие нерешённые вопросы сохранять. Сведения:

- последний подтверждённо завершённый и текущий незавершённый инкремент, отдельные статусы реализации и готовности;
- реализованный scope, незавершённые работы, решения и ограничения;
- ветка, проверенный HEAD и описание незакоммиченного diff; после commit/merge — проверять актуальный SHA через Git, не пытаться записать self-referential hash коммита в сам коммит;
- точные команды, среда/версии, exit codes, counts passed/failed/skipped, SHA/diff, ссылки на существующие отчёты/review/CI; невыполненные проверки с причиной;
- текущий PR/CI и оставшиеся действия доставки, если инкремент ещё не закрыт;
- открытые вопросы и блокеры, что требуется от владельца;
- следующий безопасный шаг, зависимости, условия старта и разрешения, которые ещё нужны.

Обновить STATUS и применимые KNOWN_GAPS, DECISIONS_PENDING, ADL, traceability, ECC_USAGE и отчёт этапа по INCREMENT_REPORT_TEMPLATE в объёме фактических изменений. Не добавлять фиктивные записи в неизменившиеся области. Не повышать статус сверх evidence и не терять незакрытые вопросы. Для read-only исследования отчёт остаётся в ответе, если запись отдельно не поручена.

Не хранить секреты, исходный контент проектов, полные промпты агентов и несущественные временные данные. Существенные выводы временных проверок переносить в постоянный отчёт; временный путь не считать гарантированно доступным следующей сессии. Canonical архитектуру автоматически не редактировать.

## 4. Проверка сценария новой сессии

Без реализации инкремента проверить по файлам и Git: (а) восстановление текущей работы; (б) выбор следующего пункта с мини-этапами; (в) зависимости и блокеры; (г) отсутствие повторного выполнения DONE; (д) необходимые проверки/review/доставка; (е) сохранение при блокировке; (ж) остановка после одного инкремента. Неразрешимая неоднозначность приводит к конкретному вопросу владельцу, а не к выбору произвольного этапа.

Критерий процесса: новая сессия восстанавливает инженерные инструкции из репозитория без длинного повторного промпта. Новые бизнес-/security-решения, недоступные обязательные gates и ограничения среды могут требовать участия владельца; процесс не обещает их автоматического обхода.
