# ADR-131 — Flash: обязательный fingerprint ожидаемой identity

| Поле | Значение |
|---|---|
| Дата / статус | 2026-11-17 / ACCEPTED Implementation Lead по прямому делегированию владельца; реализован отключённый контракт, полный G156 NOT VERIFIED |
| Основание | Ответ владельца на вопрос о составе metadata: «прими решение на основе разрабатываемого нами агента и его концепции. Прими и реализуй.» Выбор состава передан исполнителю; это не утверждение неизвестных фактических значений или профиля |
| Источники | DOC076 v1.1 §3.1/7; DOC075 §3.3; DOC078 §5.1; ADR128/130; AI RES — контролируемая инженерия требований с immutable результатами, provenance и fail-closed gates |
| Проблема | Rolling alias сам по себе не даёт сигнала изменения backend. Если принять отсутствие fingerprint как нормальное ожидание, один из доступных сигналов drift теряется. Optional candidate metadata и допустимая identity для принятия результата имеют разный смысл |
| Решение | Для Flash expectation обязателен непустой bounded safe fingerprint VALUE. Candidate observation сохраняет ABSENT/NULL/VALUE как факты, но ABSENT/NULL не становятся допустимым baseline. Missing/null/value mismatch относительно ожидаемого VALUE запрещает успешное сравнение. Fingerprint не immutable selector, не grant и не доказательство approval |
| Обязательный состав | Trusted request model id; фактические provider/routing/response model, безопасные application/provider request refs и trusted UTC observation time; отдельно immutable AI RES code/profile/config/prompt/tools refs. Точная expected provider/model tuple, fingerprint VALUE, evidence hash и generation проверяются совместно |
| Альтернативы | Optional fingerprint в expectation — отклонён для первого Flash-среза: может допустить alias-only контроль. Требовать fingerprint уже для сохранения candidate observation — отклонено: потеряет evidence отсутствия metadata. Фиктивный pin/подстановка прежнего fingerprint — запрещены |
| Реализация | IdentityExpectation.__post_init__ требует VALUE; parser и direct constructor одинаково fail-closed. JSON Schema0.2 с соответствующей expectedIdentity ветвью. Candidate extraction ничего не дополняет чужими/предыдущими значениями |
| Совместимость | Несовместимая ревизия неопубликованного WORKING internal контракта0.1→0.2. Schema0.1 сохранена без изменений, активный parser принимает только0.2. Старые evidence явно пересоздаются в новом разрешённом процессе; автоматического преобразования/повторного approval нет. В коде consumers — unit tests; product wiring/persistence отсутствуют. Public API/Worker/events/baseline/DB не меняются |
| Что остаётся за человеком | Точные реальные значения identity/fingerprint и evidence после candidate PoC, Bifrost/security acceptance и profile approval. Новый состав не утверждает первый ответ, не выдаёт права или расходы, не разрешает SLICE01 автоматически |
| Риск | Fingerprint через pinned Bifrost/SSE пока не подтверждён live. Если отсутствует/некорректен — допуск закрыт до исправления/проверки; нельзя автоматически ослабить правило. Не обнаруживаются все скрытые обновления; fingerprint может меняться по причинам backend, что требует консервативной повторной оценки |
| Область / исключения | Только отключённый metadata contract/validator/tests и implementation docs. Не реализуются этим решением durable block/generation/audit/reapproval, transport/factory wiring, budget ledger и provider calls; их план и gates сохраняются. ADR129/G107 до S20, SLICE01 до S17 |
| Проверки | RED5failures до реализации; GREEN121cases после: schema/parser/direct construction, missing/null/empty/unsafe/oversized fingerprint, candidate preservation, exact comparison, prior0.1 отказ, no autoapproval; regression/static и независимые code/security review фиксируются в отчёте |
| Пересмотр | Live route не сохраняет обязательную metadata; provider contract меняется; выход за Flash exception. Изменение технического решения — с evidence и новой версией, без silent downgrade |

Решение закрывает прежний вопрос о выборе **состава** metadata по прямому делегированию владельца. Оно не выдаёт исполнителю полномочие утвердить фактическое первое наблюдение или продуктовый профиль. Canonical документы/Registry не меняются: состав уточняется внутренним контрактом в пределах DOC076 §3.1.
