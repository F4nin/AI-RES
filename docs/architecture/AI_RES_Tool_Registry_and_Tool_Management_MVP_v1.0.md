# AI RES — Tool Registry и Tool Management Layer
## Состав и требования MVP — v1.0

**Статус:** BASELINED — архитектурный контракт; runtime acceptance остаётся обязательной проверкой. LLM Gateway с поддержкой внешних и локальных моделей (вариант C) подтверждён пользователем.

## 1. Назначение

Tool Management Layer предоставляет Manager и Workers контролируемый доступ к локальным функциям, API, готовым интеграциям, MCP-серверам и специализированным операциям платформы. Реестр описывает не просто подключённые системы, а конкретные доступные операции, их контракты, ограничения и условия применения.

Разделение ответственности:
- **Модель/агент** интерпретирует задачу, выбирает подходящий инструмент и формирует аргументы.
- **Tool Registry** хранит каталог инструментов и их метаданные/контракты.
- **Policy & Permission Engine** независимо проверяет, разрешён ли вызов конкретному субъекту в данном контексте.
- **Tool Gateway** выполняет разрешённый вызов, применяет технические политики и нормализует результат.
- **Adapter** связывает общий контракт AI RES с конкретным локальным инструментом, API, плагином или MCP-сервером.
- **Audit/Observability** фиксирует вызов, решение политики, результат, ошибки и повторные попытки.
- **Workflow Engine** управляет жизненным циклом исполнения задачи; он не заменяет Manager в содержательном выборе инструмента.

## 2. Категории инструментов

| Категория | Назначение | Применение в AI RES MVP |
|---|---|---|
| Local Tools | Детерминированные функции внутри платформы | Обязательно: парсинг/валидация, преобразования, поиск по метаданным, проверки, операции с графом/артефактами |
| API Tools | Обёртки над внутренними и внешними API | Обязательно как поддерживаемый тип; конкретные интеграции — по MVP-приоритетам |
| Plugins / готовые интеграции | Повторное использование готовых модулей | Поддержать как вариант подключения, но не делать обязательным источником инструментов |
| MCP | Стандартизированное подключение серверов инструментов/данных | Предусмотреть в MVP; подключать только доверенные и проверенные серверы |
| Stateful Tools | Операции, читающие/изменяющие устойчивое состояние | Обязательно учитывать как характеристику риска и прав, а не как отдельный транспорт |
| Runtime Code Generation | Генерация и выполнение кода во время задачи | Не включать в базовый MVP либо ограничить изолированным, выключенным по умолчанию экспериментальным режимом |

Категории не взаимоисключающие: например, MCP-инструмент может быть stateful API-операцией.

## 3. Минимальная запись Tool Registry

Каждая запись реестра должна содержать:

- `tool_id` — стабильный уникальный идентификатор;
- `name` — конкретное, однозначное имя операции;
- `description` — назначение, условия вызова и ограничения;
- `category` — local / api / plugin / mcp / code;
- `provider` и `adapter_id` — поставщик и адаптер исполнения;
- `version` и `contract_version`;
- `input_schema` и `output_schema` — машинно-проверяемые схемы (например, JSON Schema);
- `operation_type` — read / create / update / delete / execute / communicate;
- `stateful` и `side_effects`;
- `risk_level` и `reversibility`;
- `required_permissions` и допустимые роли/контексты;
- `data_classification` — типы данных, с которыми работает инструмент;
- `timeout`, `retry_policy`, `idempotency_support`, `rate_limit`;
- `availability_status` — active / disabled / degraded / deprecated;
- `health_check` и сведения о тестовой/продуктивной среде;
- владелец, документация, дата последней проверки и журнал версий.

Имена, описания и схемы являются частью интерфейса для модели: слишком общие или пересекающиеся описания повышают вероятность неверного выбора.

## 4. Обязательный поток вызова

1. Manager или Worker формирует намерение вызвать конкретную операцию.
2. Агент получает только каталог/схемы инструментов, доступные его роли и текущей задаче.
3. Выбранный инструмент и аргументы валидируются по контракту.
4. Policy & Permission Engine проверяет субъект, проект, Epic, задачу, тип операции, классификацию данных, среду и необходимость подтверждения человека.
5. При отказе вызов не выполняется; агент получает безопасную причину отказа без раскрытия секретов.
6. При разрешении Tool Gateway передаёт вызов адаптеру.
7. Адаптер исполняет операцию с ограниченными credentials и ресурсами.
8. Результат проверяется по схеме, нормализуется и возвращается вызывающему агенту.
9. Фактический результат побочного действия по возможности проверяется отдельно (например, повторным чтением состояния), а не выводится из одного лишь ответа API.
10. Событие, решение политики, результат и ошибки записываются в аудит/телеметрию.

## 5. Безопасность и полномочия

Обязательные принципы MVP:

- Least Privilege: минимальные права для роли и операции.
- Read-only по умолчанию для Brownfield и внешних исходных систем.
- Права ограничены проектом, Epic, задачей и/или конкретным запуском; временные полномочия отзываются после завершения.
- Секреты хранятся в Secrets Vault и не помещаются в prompt или обычный контекст модели.
- Разделять чтение и изменение: не предоставлять универсальный инструмент «выполнить произвольный SQL/команду», если можно предоставить узкие операции.
- Для stateful операций явно определять побочные эффекты, идемпотентность, обратимость и проверку фактического результата.
- Создание, изменение, удаление, публикация и внешняя коммуникация требуют отдельной политики; критические, необратимые и внешние действия могут требовать подтверждения человека.
- Проверять и санитизировать аргументы; использовать параметризованные запросы.
- Защищать MCP/API от неавторизованного доступа, prompt injection через результаты инструментов, SSRF, утечек данных и чрезмерных полномочий.
- Недоверенный результат инструмента трактуется как данные, а не как инструкция для агента.

## 6. Надёжность и обработка ошибок

Минимум для MVP:

- типизированные ошибки: validation, authorization, not_found, rate_limit, timeout, unavailable, conflict, execution, partial_result;
- ограниченные повторы только для временных и безопасно повторяемых ошибок;
- экспоненциальная задержка/backoff и соблюдение rate limits;
- idempotency key для операций, где повтор может создать дубликат;
- не повторять всю цепочку, если можно повторить только неудачный шаг;
- fallback только на заранее разрешённый инструмент/сервис и только если он эквивалентен по смыслу и безопасности;
- после исчерпания повторов — безопасная остановка, частичный результат или эскалация Manager;
- не считать действие выполненным по факту отправки запроса: проверять подтверждение и, где возможно, состояние целевой системы;
- сохранять успешные независимые результаты, не продолжая зависимые операции при нарушении предусловий.

## 7. Аудит и наблюдаемость

Для каждого вызова фиксировать как минимум:

- идентификаторы проекта, Epic, задачи, Worker Run и correlation/trace;
- вызывающую роль/субъект и `tool_id`/версию;
- время, длительность, среду и тип операции;
- результат проверки полномочий (allow/deny/approval-required) и policy version;
- статус исполнения, тип ошибки, число повторов и fallback;
- ссылки на входной/выходной артефакт или безопасно редактированные метаданные;
- факт побочного эффекта и результат его проверки.

Не записывать секреты и чувствительные payload целиком в обычные логи. Для содержимого применять редактирование, классификацию, контроль доступа и сроки хранения.

## 8. Выбор инструмента и оркестрация

Нужно разделять два решения:

- **Tool selection:** какой инструмент вызвать на текущем шаге (стандартный, семантический или иерархический выбор).
- **Task orchestration:** как организовать всю задачу (цепочка, ReAct, Planner–Executor, параллельное выполнение, граф).

Это совместимые уровни. Например, Manager может сформировать граф работ, а Worker на конкретном шаге — выбрать инструмент семантически из разрешённого набора.

Для MVP предлагается:
- детерминированный/явный выбор для небольшого фиксированного набора критичных инструментов;
- семантический выбор только среди предварительно отфильтрованных разрешённых инструментов, когда каталог расширяется;
- иерархический каталог/поиск при росте числа инструментов;
- передавать модели только релевантные схемы, а не весь каталог без необходимости.

Контекст вызова должен включать текущую подзадачу, ограничения, доступные схемы, результаты предыдущих шагов и критерии проверки. Контекст должен быть релевантным, структурированным, актуальным, ограниченным по объёму и сохранять происхождение данных.

## 9. Состав MVP

### Обязательно

1. Единый Tool Registry с версионируемыми машинно-читаемыми контрактами.
2. Общий интерфейс/адаптер для Local Tools и API Tools.
3. Tool Gateway как единая точка исполнения.
4. Независимый Policy & Permission Engine.
5. Разграничение read/write и stateful/side-effect операций.
6. Secrets Vault или эквивалентный защищённый механизм секретов.
7. Валидация входа и выхода по схемам.
8. Ограниченные retries, timeout, rate limit и типизированные ошибки.
9. Idempotency для поддерживаемых изменяющих операций.
10. Аудит вызовов и базовая телеметрия.
11. Каталог доступных инструментов с фильтрацией по Worker/роли/проекту/задаче.
12. Возможность отключить инструмент, версию или провайдера без изменения логики Worker.

### Поддержать архитектурно, включать по мере необходимости

- MCP-клиент и подключение доверенных MCP-серверов;
- плагины/готовые интеграции;
- health checks и circuit breaker;
- fallback-провайдеры;
- семантический выбор инструментов;
- генерацию черновых API-обёрток по OpenAPI с обязательным review и тестированием.

### Не включать в базовый MVP

- свободное выполнение произвольного кода моделью в production;
- произвольный SQL/терминал с широкими правами;
- автоматическую публикацию/удаление/изменение внешних данных без политик и требуемого подтверждения;
- автоматическое подключение непроверенных MCP-серверов;
- автоматическое принятие сгенерированных обёрток без code review и тестов.

## 10. Кандидатный набор инструментов AI RES

Начальный внутренний каталог целесообразно формировать вокруг операций платформы:

- чтение контекста проекта/Epic и истории;
- поиск/чтение источников и фрагментов с provenance;
- извлечение и нормализация файлов;
- создание/обновление черновых задач и кандидатов требований в пределах разрешений;
- чтение/создание/версионирование артефактов;
- чтение и обновление связей трассируемости;
- проверка схем, требований и диаграмм;
- запуск разрешённых workflow/Worker tasks через Workflow Engine;
- получение статуса задач и результатов;
- запрос подтверждения человека;
- формирование отчётов и уведомлений.

Это предложения по функциям платформы, а не окончательный перечень API/эндпоинтов. Их границы и контракты следует определить при проектировании доменной модели и API AI RES.

## 11. Решения и открытые вопросы

### Подтверждено в обсуждении

- Workers получают ролевые наборы инструментов, соответствующие их специализации.
- Manager может временно расширять доступный конкретному Worker набор инструментов для определённой задачи, только в пределах политик и разрешений.
- Cloudflare Code Mode включается в архитектурное рассмотрение как механизм композиции и программного выполнения последовательностей инструментальных вызовов; это не отдельный источник инструментов и не замена API/MCP.

### Предлагается принять как архитектурные принципы

- централизованный Tool Management Layer;
- общий контракт инструментов;
- разделение Registry, Policy Engine, Gateway, Adapters, Audit и Secrets;
- Manager выбирает, Policy Engine разрешает/запрещает, Gateway исполняет;
- MCP и Code Mode — разные, дополняющие способы расширения, а не взаимозаменяемые понятия;
- права не наследуются автоматически между Workers и не расширяются самим Worker.

### Остаётся определить

- точную модель ролей и permission scopes;
- какие операции требуют human approval и при каких уровнях риска;
- конкретные интеграции MVP и их владельцев;
- формат общего Tool Contract и версионирование;
- перечень допустимых MCP-серверов и требования к их сертификации;
- правила хранения payload аудита и сроки retention;
- численные лимиты timeout/retry/rate/token/cost;
- окончательный выбор реализации Code Mode и его границы в MVP (Cloudflare Code Mode — кандидат для пилота; production-использование требует отдельной оценки зрелости и ограничений);
- перечень платформенных инструментов первой реализации.

Не следует выдавать эти детали за дословные требования книги.


## 13. Ролевые наборы инструментов Workers

### 13.1. Принцип

Каждый Worker получает не общий каталог всех инструментов AI RES, а разрешённый набор, соответствующий его специализации, задаче, контексту проекта и текущему уровню полномочий. Это уменьшает поверхность атаки, снижает шум в контексте модели и помогает точнее выбирать инструменты.

Ролевой набор — это не жёсткая привязка «одна роль = один неизменный список». Он состоит из:
- базового набора роли;
- инструментов, разрешённых для конкретного проекта;
- временных инструментов, предоставленных Manager под конкретную задачу/Worker Run;
- явных запретов и ограничений.

### 13.2. Предварительные профили

| Worker | Базовые категории инструментов (кандидатный состав) | Ограничения по умолчанию |
|---|---|---|
| Elicitation | чтение контекста Epic, история диалога, создание вопросов/заметок, регистрация ответов и открытых вопросов | не утверждает требования и не меняет бизнес-решения |
| Research | поиск и чтение источников, web/API read, Git read, извлечение документов, provenance | внешние источники считаются недоверенными; запись во внешние системы закрыта |
| Business Analysis | чтение/анализ процессов, ролей, правил, создание черновиков моделей и артефактов | не утверждает бизнес-правила и scope |
| Requirements | чтение/создание/изменение черновиков требований, классификация, связи трассируемости, проверки качества | утверждение требований и Baseline недоступно |
| System Analysis | чтение архитектурного контекста, модели данных, схемы, анализ зависимостей, черновики моделей | изменение архитектурных решений — только через согласованный процесс |
| API & Integration | OpenAPI, JSON Schema, API catalog, контрактные тесты, чтение спецификаций и тестовых сред | production write-вызовы закрыты по умолчанию |
| Modeling & Diagram Validation | генерация/валидация UML, BPMN, ERD, C4 и других применимых диаграмм | запись только в черновые версии артефактов |
| Quality Assurance | валидаторы, тестовые наборы, schema checks, consistency/traceability checks, evaluation tools | не изменяет проверяемый результат молча; дефекты оформляет отдельно |
| Traceability & Change | чтение/построение графа связей, impact analysis, подготовка Change Request | не утверждает CR и не применяет изменения Baseline самостоятельно |

Manager получает инструменты управления задачами, планом, статусами, контекстом, распределением Workers, проверкой результатов и запросом human approval. Manager не получает через этот профиль обходных полномочий для изменения бизнес-решений или Baseline.

Эта таблица — архитектурная проектная раскладка для AI RES, а не утверждение, что именно такой перечень предписан книгой. Конкретные tool IDs, схемы и permission scopes будут определяться отдельно.

### 13.3. Временное расширение набора

Manager может запросить временное добавление инструмента Worker, если:
- инструмент необходим для конкретной задачи;
- назначение и ожидаемый результат явно указаны;
- Policy & Permission Engine подтверждает доступ;
- scope ограничен проектом, задачей, Worker Run, операциями и временем;
- все вызовы попадают в общий аудит.

Временное расширение не меняет постоянный профиль роли и автоматически прекращается по завершении/отмене Worker Run или истечении срока. Worker не может сам выдать себе дополнительный инструмент или расширить его scope.

## 14. Cloudflare Code Mode как механизм композиции инструментов

### 14.1. Что это такое

Cloudflare Code Mode рассматривается как один из возможных runtime-механизмов, в котором модель вместо последовательного выбора отдельных инструментов получает один инструмент исполнения кода и формирует JavaScript-план, вызывающий типизированные инструменты, передающий между ними результаты, выполняющий ветвления, циклы, фильтрацию и преобразование данных.

Это **не** отдельный тип Tool Source и не замена Local/API/Plugin/MCP. Следует независимо различать:
1. **Источник инструмента:** внутренний Local/API или внешний MCP/Plugin.
2. **Интерфейс модели:** прямые tool calls либо Code Mode.
3. **Место исполнения реализации:** серверная среда, браузер, отдельный сервис/агент или иной runtime.

Инструменты из разных источников могут предоставляться как прямыми вызовами, так и через Code Mode, если конкретная интеграция это поддерживает.

### 14.2. Где Code Mode может быть полезен AI RES

- Research Worker: последовательный поиск по нескольким разрешённым источникам, фильтрация и объединение результатов.
- API & Integration Worker: получение нескольких спецификаций, сопоставление схем и подготовка сводного результата.
- QA Worker: запуск набора независимых валидаторов, сбор и нормализация результатов.
- Traceability Worker: пакетное чтение связей, вычисление влияния и формирование структурированного отчёта.
- Manager: композиция read-only операций для сбора состояния Epic и подготовки сводки.

Для простой одиночной операции прямой вызов инструмента предпочтительнее. Code Mode оправдан при композиции зависимых вызовов, ветвлении, циклах, progressive discovery или сокращении промежуточных данных, передаваемых в контекст модели.

### 14.3. Cloudflare Code Mode: свойства и ограничения

По актуальной документации Cloudflare:
- `@cloudflare/codemode` предоставляет типизированные интерфейсы инструментов и единый code-execution tool для модели;
- сгенерированный код выполняется в изолированном Dynamic Worker sandbox;
- вызовы инструментов маршрутизируются из sandbox в host через Workers RPC;
- внешний сетевой доступ может быть заблокирован по умолчанию (`globalOutbound: null`), чтобы код обращался к возможностям только через явно предоставленные инструменты;
- предусмотрены варианты интеграции с AI SDK, TanStack AI, MCP и OpenAPI;
- Code Mode обозначен Cloudflare как experimental и может иметь breaking changes.

Следовательно, для AI RES Cloudflare Code Mode следует считать **кандидатом для ограниченного технического пилота**, а не безусловно утверждённой production-зависимостью.

### 14.4. Обязательные защитные границы

- Code Mode получает только уже разрешённый ролевой/временный набор инструментов; sandbox не является источником полномочий.
- Каждый фактический вызов проходит через общий Policy Engine и Tool Gateway либо эквивалентный enforcement point.
- Секреты не передаются в исполняемый код и LLM-контекст; секретами управляет host-side adapter/secret vault.
- Сетевой доступ из sandbox запрещён по умолчанию; исключения — только через контролируемые сетевые посредники.
- Ограничиваются время исполнения, вычислительные ресурсы, размер входа/выхода, количество вызовов и стоимость.
- Запрещены произвольный доступ к БД, файловой системе, shell и внутренней сети вне явных инструментов.
- Все операции имеют correlation/execution ID, task ID, worker ID, tool ID, версию схемы и аудит.
- Результаты кода и вызовов валидируются; ошибки, частичные результаты и side effects явно отражаются.
- Повторное исполнение должно учитывать idempotency и не повторять необратимые действия.
- Код модели считается недоверенным входом: изоляция runtime не заменяет валидацию аргументов, авторизацию и защиту от prompt injection.

**Human approval:** действия, требующие подтверждения человека, должны проходить через отдельный approval workflow платформы. Нельзя считать, что любая реализация Code Mode автоматически умеет безопасно приостанавливать и возобновлять код перед каждым side effect. До подтверждения поддержки такого сценария в выбранной версии runtime инструменты с обязательным human approval следует вызывать прямым tool calling или через проверенный durable approval flow.

### 14.5. Предлагаемая позиция для MVP

- Архитектурно предусмотреть возможность Code Mode как альтернативного интерфейса модели к Tool Registry.
- Не делать Code Mode обязательным для всех Workers и всех вызовов.
- Начать пилот с read-only инструментов и ограниченных композиций.
- Не предоставлять через пилот production write, удаление, публикацию, утверждение требований/Baseline или другие критические side effects.
- Сравнить с прямыми вызовами по корректности, трассируемости, latency, стоимости, надёжности, качеству аудита и безопасности.
- Переводить в более широкое использование только после security review, benchmark, regression и проверки recovery/approval сценариев.

## 16. Уточнение связи с LLM Gateway и Security Architecture (v0.3)

- Manager/Workers не получают provider API keys и не вызывают provider endpoints напрямую.
- Вызов модели проходит через внутренний LLM Gateway Adapter, policy/rules checks и единый LLM Gateway.
- Принято пользователем: Gateway должен поддерживать внешние API и локальные модели; MVP использует один выбранный режим/провайдер.
- Gateway отвечает за техническую маршрутизацию; AI RES Policy & Permission Engine определяет допустимость передачи данных и полномочия субъекта.
- Model fallback разрешён только на заранее allowlisted profile и после повторной проверки data classification/egress policy.
- Tool/Connector Gateway и LLM Gateway — разные логические контуры: первый исполняет операции, второй маршрутизирует inference.
- Полная модель threat controls приведена в `AI_RES_Security_Architecture_v1.0.md` и `AI_RES_Threat_Model_v1.0.md`.

## 17. Статус

Документ описывает проектные требования к Tool Management Layer. Конкретные ACL schema, IdP, secret broker, MCP server isolation и численные лимиты остаются предметом реализации/PoC. Нельзя трактовать регистрацию инструмента в Registry как предоставление полномочий: runtime authorization выполняется отдельно перед каждым вызовом.

# Дополнение v1.0 — нормативное решение Tool Gateway и MCP

Статус: BASELINED. Применять совместно с `AI_RES_Architecture_Completion_and_Baseline_Decisions_v1.0.md`.

1. Tool Registry — каталог versioned ToolDefinition, не grant store.
2. Каждый вызов выполняется через Tool Gateway/Adapter; Manager/Worker не имеют произвольного egress.
3. Перед каждым вызовом Policy & Permission Engine проверяет subject, WorkerRun grant, resource, operation, data classification, environment, expiry и approval requirement.
4. Tool schema version pin-ится в WorkerRunEnvelope; input/output проходят schema validation и size limits.
5. Side-effecting tools требуют idempotency key, explicit side-effect classification, precondition/postcondition, timeout, retry safety and audit.
6. MCP допускается как adapter protocol, но server/tool discovery не означает доверие. Только allowlisted servers/tools, pinned configuration, scoped credentials, network allowlist, per-call auth, output validation and audit.
7. Cloudflare Code Mode/runtime code generation не входит в MVP. Отдельный sandbox PoC допускается только после threat review.
8. MVP tool families: project/domain read, source read/search, controlled domain write commands, artifact generation/validation, GitHub/GitLab read-only, OpenAPI parser/validator, diagram renderer/validator, evaluation utilities. Реальные grants задаются по Worker role/task class и не являются общими.
