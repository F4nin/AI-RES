# AI RES — Интеграции с внешними системами и управление проектным контекстом

**Версия:** 1.2  
**Статус:** BASELINED — MVP connector scope and read-only boundary; provider-specific contracts remain WORKING
**Область:** внешние системы, коннекторы, синхронизация, сопоставление объектов, источник истины, безопасность, управление изменениями и UX.

## 1. Назначение и границы

Документ определяет, как AI RES подключается к корпоративным и внешним системам, получает и обновляет проектные данные, связывает внешние объекты с доменной моделью AI RES и безопасно использует полученный контекст при работе Manager и Workers.

Это не спецификация конкретного Jira/GitHub/Confluence API и не окончательный выбор поставщика. Интеграционный слой должен позволять добавлять системы без изменения логики Manager и Workers. Точные API-контракты, scopes, лимиты, SLA и поддерживаемые версии фиксируются в паспорте каждого коннектора.

Связанные документы: `AI_RES_Source_and_Context_Lifecycle_v1.1.md`, `AI_RES_Agent_Architecture_Concept_v3.3.md`, `AI_RES_UX_Concept_v1.0.md`, `AI_RES_MVP_Capability_Matrix_v2.0.md`, `AI_RES_Requirements_Lifecycle_v1.9.md`, `AI_RES_Tool_Registry_and_Tool_Management_MVP_v0.2.md`.

## 2. Рекомендуемое архитектурное решение

**Рекомендация:** построить единый Connector Platform (логический интеграционный слой) с реестром коннекторов, адаптерами систем, единым контрактом синхронизации, шлюзом вызова операций и независимой проверкой политик. Не давать Manager/Worker прямой произвольный доступ к API внешних систем.

Логические компоненты:

1. **Connector Registry** — каталог систем и коннекторов, версии адаптеров, поддерживаемые объекты/операции, владельцы, статусы, health, ограничения и документация.
2. **Connector Adapter** — адаптер конкретной системы; переводит внешний API/события в нормализованный внутренний контракт.
3. **Connector Gateway** — единая точка исполнения операций; проверяет контракт, идентичность, разрешённую операцию, лимиты, тайм-ауты и результат.
4. **Identity & Credential Broker** — безопасное получение/обновление учётных данных и привязка подключения к пользователю/организации/сервисной идентичности.
5. **Sync Orchestrator** — планирование polling, приём webhook, ручную синхронизацию, курсоры, дедупликацию, повторы и reconciliation.
6. **External Object Mapper** — сопоставление внешних объектов с Project/Epic/Task/Requirement/Source/Artifact и хранение внешних ID.
7. **Source Authority & Ownership Registry** — правила владения типами данных и полями, авторитетность и направление синхронизации.
8. **Policy & Permission Engine** — отдельная авторизация каждого чтения/изменения, включая права пользователя и AI RES.
9. **Audit & Observability** — журнал действий и технические/качественные метрики интеграций.

Это логические границы, а не обязательное разбиение на микросервисы. Для MVP допустим модульный монолит с отдельными контрактами и границами безопасности.

### 2.1. Принцип доступа через узкие операции

Внешний API не публикуется модели как универсальный HTTP-клиент. Адаптер предоставляет небольшие типизированные операции с валидируемыми входами и выходами, например `list_repository_changes`, `get_issue`, `search_pages`, `get_openapi_spec`. Для записи — только отдельные конкретные команды, а не универсальный `update_any_object`.

Схема операции включает: назначение; допустимые роли/системы; тип операции; входную и выходную JSON Schema; требуемые scopes; классификацию данных; побочные эффекты; идемпотентность; тайм-аут; retry policy; необходимость подтверждения; проверку результата; коды ошибок и версию контракта.

## 3. Классы интеграций и выбор способа подключения

| Подход | Когда применять | Рекомендация для AI RES |
|---|---|---|
| Готовый официальный коннектор/SDK | Есть поддерживаемый поставщиком API/SDK и приемлемая модель безопасности | Предпочтительно для стандартных систем; проверять права, сопровождение и лицензию |
| Прямой API через собственный адаптер | Нужен точный контроль контракта, версий, scopes и поведения | Основной путь для ключевых интеграций |
| MCP | Несколько клиентов/агентов должны повторно использовать стандартизированный набор инструментов | Дополнительный интерфейс/транспорт, не замена авторизации и контроля; не делать обязательной основой MVP |
| Plugin/платформенная интеграция | Готовый модуль закрывает сценарий и прошёл оценку | Допустим после проверки происхождения, разрешений, обновлений и данных |
| Local tool/SDK | Система локальна или требуется контролируемая обработка файлов/репозитория | Использовать в доверенном runtime с ограничениями ресурсов и сети |
| Генерация API-обёртки | Есть стабильная OpenAPI-спецификация и много однотипных операций | Генерировать черновик, затем ревью, тесты и security review; не публиковать автоматически |
| Runtime code generation | Исключительный сценарий динамического инструмента | Не входит в MVP; изолированная песочница, deny-by-default network, лимиты и аудит |

MCP не является механизмом предоставления прав: доступ к MCP tool всё равно проходит через Policy & Permission Engine и Connector Gateway. Сам факт наличия MCP-сервера не означает, что его можно считать доверенным.

## 4. Интеграционные сценарии и направления данных

Разделять три направления:

- **Inbound** — чтение/получение внешних данных в AI RES. Основной сценарий MVP.
- **Outbound** — отправка созданных в AI RES данных во внешнюю систему. После MVP, с контролем подтверждений и конфликтов.
- **Bidirectional** — синхронизация в обе стороны. Не включать по умолчанию: требует явного владения объектами/полями, разрешения конфликтов, аудита и защиты от циклов.

Синхронизация может быть полной начальной загрузкой, инкрементальной, ручной, по расписанию или event-driven. Webhook рассматривается как сигнал о возможном изменении, после которого AI RES получает актуальное состояние через API. Payload webhook не становится автоматически доверенной полной версией объекта.

## 5. Источник истины и владение данными

**Рекомендация:** не назначать одну систему глобальным Source of Truth для всего проекта. Владение задаётся на уровне типа объекта и, при необходимости, отдельных полей/атрибутов.

Для каждой интеграционной связи задаются:

- `object_type` и `field_scope`;
- `system_of_record` — система, авторитетная для данного типа/поля;
- `ownership_mode` — EXTERNAL, AI_RES, SHARED или READ_ONLY_MIRROR;
- `sync_direction` — INBOUND, OUTBOUND, BIDIRECTIONAL;
- `conflict_policy` — правило разрешения конфликтов;
- `effective_from` / `effective_to` и владелец политики;
- правила статуса/версии и удаления.

Примеры рекомендуемой стартовой модели:

| Объект/данные | Рекомендуемое владение |
|---|---|
| Исходный код, commits, pull/merge requests | GitHub/GitLab; AI RES — read-only зеркало/источник свидетельств |
| Текущие внешние задачи/тикеты Jira | Jira; AI RES хранит сопоставление и аналитические связи, не переписывает тикет в MVP |
| Страницы Confluence/корпоративной базы знаний | Исходная система; AI RES хранит неизменяемые версии/ссылки и извлечённые утверждения |
| Требования AI RES, Decisions, Assumptions, Risks, Traceability | AI RES — каноническая доменная модель, пока явно не настроен внешний владелец |
| OpenAPI/AsyncAPI и схемы | По каждому артефакту: AI RES Native Spec либо внешний репозиторий/registry; один явно назначенный владелец |
| Утверждения, извлечённые из внешних материалов | Исходный фрагмент принадлежит источнику; Derived Finding/Candidate Requirement принадлежит AI RES |

Если один объект представлен в нескольких системах, хранить External Object Mapping: provider, tenant/instance, object type, external ID, canonical AI RES ID, URL, last observed version, mapping status, mapping provenance и время синхронизации. Не связывать объекты только по совпадению названий.

## 6. Конфликты и reconciliation

Не применять правило «последнее изменение побеждает». При конфликте:

1. определить тип объекта/поля и настроенного владельца;
2. сравнить версии, timestamps, версии источника и формальные статусы;
3. учесть provenance, права автора и scope;
4. применить формальную Conflict Policy;
5. если конфликт однозначно разрешим и низкорисков — применить разрешённое правило и записать объяснение;
6. иначе сохранить обе версии, создать Conflict/Issue или Pending Decision, показать варианты и последствия уполномоченному человеку.

Для SHARED/BIDIRECTIONAL запрещать автоматическое перезаписывание при одновременном редактировании без заданного правила слияния. Слияние текстовых/структурных объектов должно быть типизированным и проверяемым; если безопасное слияние невозможно — ручное разрешение.

Удаление во внешней системе не должно сразу физически удалять Source/Artifact в AI RES. Сначала фиксируется tombstone/deletion event, проверяются зависимости, retention и политика удаления; затем объект помечается недоступным/удалённым согласно правилам. История и audit сохраняются в допустимом объёме.

## 7. Синхронизация и согласованность

### 7.1. Рекомендуемая стратегия

Гибридная модель:

- webhook/event — быстро сообщает о потенциальном изменении;
- incremental polling — обнаруживает пропущенные события и сверяет курсоры;
- manual sync — доступна аналитику/администратору для точечной актуализации;
- periodic reconciliation — сравнивает выборочное/полное состояние внешней системы с реестром AI RES.

Не полагаться исключительно на webhook: события могут теряться, дублироваться, приходить не по порядку или содержать только ссылку на изменившийся объект. Polling-only допустим для систем без webhook или на первом этапе, но учитывает лимиты API и допустимую задержку.

### 7.2. Надёжность

- Идемпотентность обработки событий и повторных запросов.
- Хранение sync cursor/checkpoint и внешних version markers (commit SHA, ETag, updated timestamp или эквивалент).
- Дедупликация webhook по event ID и/или устойчивому ключу.
- Ограниченные retries с exponential backoff и jitter только для временных ошибок.
- Уважение `Retry-After` и API rate limits.
- Circuit breaker/пауза при устойчивой недоступности; не создавать retry storm.
- Dead-letter queue или эквивалент для событий, требующих диагностики.
- Отдельная обработка 401/403 (доступ), 404/deleted (объект), 409 (конфликт), 429 (лимит), 5xx/network timeout (временная ошибка), schema drift (контракт изменился).
- Частичная синхронизация явно маркируется; нельзя объявлять её полной.
- Порядок событий и повторная доставка не должны приводить к откату на старую версию.

### 7.3. Версии и контекст

Каждая полученная версия создаёт Source Version либо фиксирует неизменяемый внешний version marker и достаточные данные для воспроизводимости. Изменение источника запускает существующий pipeline: Change Set → deterministic checks → semantic Impact Assessment → Revalidation Plan → при необходимости новый Context Package Version и QA/Worker Run.

Worker Run продолжает использовать свой immutable Context Package. Внешнее обновление не меняет контекст уже запущенного Run и не переписывает утверждённые требования, артефакты или Baseline.

## 8. Безопасность, идентичность и управление доступом

### 8.1. Идентичности

Разделять:
- пользователя AI RES;
- подключение/учётную запись внешней системы;
- сервисную идентичность AI RES;
- Manager/Worker Run, инициировавший операцию.

Рекомендуемый порядок: OAuth 2.0/OIDC с минимальными scopes и delegated/on-behalf-of access, если поддерживается; для GitHub/GitLab — официальная app installation / fine-grained token с ограниченными репозиториями и правами. PAT широкого действия — не предпочтительный вариант; если без него нельзя, ограничить scope, срок, владельца и ротацию.

### 8.2. Обязательные требования

- Least privilege и read-only по умолчанию.
- Авторизация каждого вызова на серверной стороне, не только при подключении.
- Проверка доступа с учётом пользователя, организации, проекта, Epic, задачи, объекта и операции.
- Секреты в Secrets Vault/host-side secret store; никогда не включать токены, refresh tokens, cookies и client secrets в prompt, Context Package, логи или результаты Worker.
- Шифрование при передаче и хранении; ротация, отзыв, expiry и аудит credentials.
- Проверка подписи webhook, защита от replay и ограничение допустимых источников/адресов.
- Защита от SSRF, DNS rebinding, небезопасных redirect, чрезмерных ответов и вредоносных файлов.
- Изоляция tenant/organization; ACL применяется до retrieval и до формирования контекста.
- Маскирование персональных/секретных данных в логах и телеметрии.
- Учитывать data residency, retention, deletion и ограничения передачи данных внешним LLM/API по политикам организации.
- Внешние материалы — недоверенные данные: prompt injection в issue, README, wiki, комментариях и API-ответах не меняет системные инструкции, политики и разрешения.

### 8.3. Запись во внешние системы

В MVP все внешние коннекторы работают read-only. В дальнейшем любая write-операция должна быть отдельным типизированным действием с preview/diff, объектом назначения, перечнем полей, оценкой последствий, проверкой полномочий, подтверждением уполномоченного человека для значимых действий, идемпотентным ключом, audit record и postcondition verification.

Manager может подготовить Change Proposal и запросить разрешение; он не может сам выдать себе право, обойти Policy Engine или использовать чужую пользовательскую сессию. Повтор после timeout не должен создавать дубликат: сначала проверяется фактическое состояние операции.

## 9. Архитектура контекста и mapping

Внешний объект не должен напрямую становиться доменным объектом AI RES без проверки и маппинга. Pipeline:

1. получить внешний объект через адаптер;
2. проверить ACL, tenant, схему и целостность;
3. определить внешний ID и версию;
4. сопоставить с существующим External Object Mapping либо предложить новый mapping;
5. сохранить Source/Source Version/Fragment и provenance;
6. нормализовать внешние поля в каноническое представление;
7. применить ownership/conflict policy;
8. индексировать только разрешённые фрагменты;
9. при изменении выполнить diff и Impact Assessment;
10. включить в Context Package только актуальные, разрешённые и релевантные сведения с версией и локатором.

Нормализация не должна уничтожать исходное значение, внешний формат, идентификатор, URL, timestamp или семантику статусов. Хранить raw snapshot/ссылку на версию отдельно от normalized projection. Сопоставление статусов/пользователей/приоритетов выполнять через versioned mapping tables, а неизвестное значение сохранять как UNKNOWN, не угадывать.

## 10. UX интеграций

Раздел «Интеграции» в Project/Organization Settings показывает:
- подключённые системы и область действия;
- статус соединения и последнюю успешную синхронизацию;
- владельца подключения и срок действия доступа без раскрытия секретов;
- доступные типы данных и разрешённые операции;
- направление и режим синхронизации;
- ошибки/ограничения и следующее полезное действие.

Подключение — пошаговый понятный сценарий: выбрать систему → пройти авторизацию у поставщика → выбрать разрешённые проекты/репозитории/пространства → показать scopes простым языком → проверить соединение → выбрать, какие данные включить в проект → подтвердить режим синхронизации. Не просить пользователя копировать токены в чат.

На карточке внешнего источника показывать внешнюю систему, объект/URL, владельца/авторитетность, версию/последнюю синхронизацию, статус актуальности, scope доступа, provenance и влияние изменений. При конфликте показывать различия и последствия, а не технические payload/API-логи по умолчанию.

Уведомления группировать: доступ отозван; синхронизация требует внимания; обнаружено существенное изменение; конфликт требует решения; критическое влияние требует QA/аналитика. Не уведомлять о каждом webhook/API call.

## 11. Ошибки и деградация

Состояния интеграции должны различать CONNECTED, DEGRADED, AUTH_REQUIRED, PERMISSION_REVOKED, RATE_LIMITED, SYNC_FAILED, PARTIAL_SYNC, SCHEMA_CHANGED, DISCONNECTED (названия предварительные).

При недоступности внешней системы AI RES может использовать последний успешно полученный снимок только с явным указанием версии и времени синхронизации. Если требование задачи предполагает актуальные данные, устаревший снимок не считается достаточным: задача блокируется/эскалируется либо пользователь явно принимает ограничение. Нельзя молча выдавать старые данные за актуальные.

Изоляция отказов: сбой одного коннектора не должен останавливать независимые интеграции и задачи. Manager выбирает содержательный recovery; Sync Orchestrator выполняет retries/checkpoints; Policy Engine сохраняет fail-closed поведение для операций, где доступ не подтверждён.

## 12. Мониторинг и эксплуатация

Минимальные метрики на каждый connector/provider/tenant (с безопасной кардинальностью):
- доступность и health;
- успешные/неуспешные операции по типу и коду ошибки;
- sync lag, время последней успешной синхронизации;
- количество обработанных, дублированных, пропущенных и отложенных событий;
- частота 401/403/404/409/429/5xx и schema drift;
- retries, circuit breaker, DLQ depth;
- полнота синхронизации и расхождения reconciliation;
- задержка P50/P95/P99, throughput и стоимость;
- ошибки mapping и конфликты;
- нарушения ACL/попытки доступа (без утечки содержимого).

Трассировка должна связывать user request → Manager plan/task → Worker Run → connector operation → provider response → Source Version/Change Set → Impact Assessment. Общие correlation IDs; секреты и полные чувствительные payloads не логировать.

## 13. MVP и этапы развития

### MVP — рекомендованный объём

1. Connector Registry и общий внутренний контракт; архитектурная возможность добавлять адаптеры без изменения Manager/Workers.
2. GitHub/GitLab read-only для выбранных репозиториев и разрешённых scopes: файлы, commits/diffs, ветки/теги и базовые PR/MR metadata — только если доступно и нужно сценарию.
3. Поддержка ручного обновления и ограниченного polling; webhook — предусмотреть интерфейс и безопасность, включать при готовности адаптера.
4. Импорт OpenAPI/Swagger как файла/URL с контролем источника и версий; прямое периодическое API-получение — по необходимости конкретного проекта.
5. External Object Mapping для Source/Source Version и выбранных сущностей; стабильные external IDs.
6. Read-only, ACL, OAuth/app credentials или безопасный эквивалент, Secrets Vault, аудит.
7. Sync checkpoints, идемпотентность, ограниченные retries/backoff, partial sync и видимый статус.
8. Diff/Change Set и запуск существующего Impact Assessment/revalidation pipeline.
9. UI подключения/состояния интеграции и ошибок.

### После MVP

- Jira read-only: проекты, задачи, статусы, связи, история изменений в пределах scopes.
- Confluence/SharePoint/корпоративные базы знаний: страницы, вложения, версии, ACL-aware retrieval.
- Webhooks и полноценная reconciliation для поддерживаемых систем.
- Дополнительные API management/registry, базы данных и корпоративные системы.
- Управляемый outbound для ограниченных сценариев (например, создание draft issue или публикация согласованного артефакта) через Change Proposal и human approval.
- Bidirectional sync только для выбранных типов/полей после отдельного анализа конфликтов.

### Не включать в MVP

- произвольный API-клиент, SQL или shell для модели;
- широкие write/delete scopes;
- автоматическую двустороннюю синхронизацию;
- автоматическое слияние конфликтующих бизнес-требований;
- автоматическую публикацию/изменение Baseline;
- runtime code generation как обязательную часть;
- GraphRAG или отдельную распределённую платформу интеграций без подтверждённой нагрузки.

## 15. Критерии приёмки интеграционного контура

1. Подключение не раскрывает секреты пользователю или модели.
2. Любая операция проверяется по актуальным правам и scope.
3. Невалидные/неразрешённые объекты не попадают в retrieval/Context Package.
4. Повторное webhook-событие не создаёт дубликаты и не откатывает версию.
5. Пропущенное событие обнаруживается polling/reconciliation в пределах согласованного окна.
6. Частичная синхронизация явно отображается и не маркируется как полная.
7. Отозванный доступ приводит к AUTH_REQUIRED/PERMISSION_REVOKED и блокирует защищённые операции.
8. При конфликте сохраняются обе версии и создаётся объяснимый Conflict/Pending Decision; last-write-wins не применяется без политики.
9. Изменение внешнего источника создаёт версию/Change Set и запускает Impact Assessment.
10. Worker Run сохраняет неизменный Context Package Version.
11. Недоступность коннектора не останавливает независимые задачи.
12. Для каждого существенного действия доступны actor, operation, target, timestamp, policy decision и correlation ID без секретов.
13. Устаревшие данные не выдаются за актуальные; требование свежести проверяется для задачи.
14. Контракт адаптера покрыт тестами success, validation, auth, rate limit, timeout, schema drift, duplicate event и recovery.

## 16. Решения, рекомендации и открытые вопросы

### Ранее зафиксированные положения проекта
- Источники и Source Versions неизменяемы; обновление создаёт новую версию.
- Brownfield-репозитории по умолчанию read-only.
- Context Package Version неизменяем для каждого Worker Run.
- Policy & Permission Engine независимо проверяет права.
- Интеграции должны учитывать provenance, ACL, prompt injection, секреты и аудит.
- Изменение источника запускает impact assessment, но не переписывает утверждённые требования/Baseline.

### Рекомендации данного блока (не считать утверждёнными решениями пользователя)
- Единая Connector Platform с Registry, Adapters, Gateway, Sync Orchestrator и External Object Mapper.
- MVP read-only; GitHub/GitLab — первая внешняя интеграция; Jira/Confluence — следующий этап.
- Гибрид webhook + polling + manual sync + reconciliation.
- Source of Truth на уровне типа объекта/поля, а не глобально.
- OAuth/OIDC/app installation с минимальными scopes; секреты в Vault.
- Outbound и bidirectional sync только после MVP и только через типизированные операции, preview, approval и audit.

## 17. Методологическая основа и границы

**Из главы 4 «Инструменты»:** классификация Local/API/Plugin/MCP/stateful tools; узкие контракты; оценка API, scopes, аутентификации, rate limits, ошибок, повторов, проверки результата, аудита и реестра инструментов. AI RES применяет эти принципы к платформенному Connector Layer.

**Из главы 5 «Оркестрация ИИ-агентов»:** Manager выбирает маршрут и recovery, Workflow/исполнительный слой управляет состояниями, повторами, лимитами и handoff. Внешняя синхронизация не должна превращать Manager в исполнителя API-вызовов.

**Из главы 6 «Знания и память ИИ-агентов»:** раздельные конвейеры записи и чтения, retrieval с фильтрацией по доступам, гибридный поиск, provenance, актуальность и оценка качества. Connector ingestion поставляет данные в Source/Knowledge pipeline, а не заменяет его.

**Из главы 10 «Мониторинг»:** мониторинг внешних API, ошибок инструментов, задержек, retries, fallback, сквозные traces и связь с эксплуатационными метриками.

Книга задаёт принципы и чек-листы, но не предписывает предложенную доменную модель Connector Platform, список MVP-поставщиков, ownership modes, статусы и критерии приёмки. Это адаптация и проектные рекомендации AI RES. Внешние стандарты/продукты здесь не исследовались; конкретные версии API и технологии требуют отдельной проверки при реализации.
