# 1. Зачем агенту нужна оркестрация

Оркестрация — логика, управляющая тем, как агент использует модель, инструменты, базы данных, память и другие компоненты для выполнения задачи. Это не только выбор инструмента. Оркестрация определяет:

- какие шаги выполнить и в каком порядке;
- какие шаги можно выполнять одновременно;
- какую информацию передать модели на каждом этапе;
- когда повторить действие, изменить план или запросить уточнение;
- как проверить промежуточный результат;
- когда остановиться, сформировать ответ или передать решение человеку.

Для простой задачи достаточно одного вызова инструмента и минимального контекста. Для сложной задачи потребуются планирование, декомпозиция, извлечение данных из памяти, динамическая сборка контекста и контроль выполнения.

**Главный принцип:** выбирайте самый простой способ оркестрации, который надёжно выполняет задачу. Сложность сама по себе не делает агента лучше.

## 1.1. Два уровня, которые нельзя путать

| Уровень | Вопрос | Примеры |
|---|---|---|
| Выбор инструмента | Какую функцию вызвать сейчас? | Стандартный, семантический, иерархический выбор |
| Оркестрация задачи | Как организовать весь процесс? | ReAct, планировщик–исполнитель, параллельное выполнение, цепочка, граф |

Можно использовать семантический выбор инструментов внутри ReAct, а затем выполнять выбранные инструменты параллельно или в графе. Это взаимодополняющие уровни.

# 2. Типы агентов и стратегии рассуждения

В книге описаны шесть архетипов. Это не взаимоисключающие «виды моделей», а схемы поведения агента; на практике их можно комбинировать.

## 2.1. Рефлекторный агент (Reflex Agent)

**Суть:** прямое соответствие между входным сигналом и действием. Агент не строит многошаговое рассуждение, а действует по правилам «если условие — то действие».

**Как работает:** получает сообщение/событие → проверяет триггер → выбирает связанное действие → вызывает инструмент или возвращает фиксированный результат.

**Пример:** если пользователь пишет «статус заказа», вызвать `get_order_status`; если сообщение содержит `/help`, показать справку.

**Когда применять:** маршрутизация по ключевым словам или чётким признакам, одношаговый поиск, простая автоматизация, обработка событий с заранее известной реакцией.

**Преимущества:** минимальная задержка, предсказуемость, низкая стоимость, простое тестирование.

**Ограничения:** не подходит для неоднозначных запросов, длинных цепочек и задач, где следующий шаг зависит от результата предыдущего.

**Практический вывод:** если задачу можно надёжно описать правилами, не нужно поручать её автономному LLM-агенту. Используйте программную маршрутизацию или рефлекторную схему.

## 2.2. ReAct (Reason + Act)

**Суть:** модель итеративно чередует рассуждение и действие. Она выбирает инструмент, получает наблюдение, анализирует результат и решает, что делать дальше.

**Цикл:** цель и контекст → следующий полезный шаг → выбор инструмента и аргументов → выполнение → наблюдение → обновление контекста → повтор или завершение.

**Пример:** пользователь просит выяснить причину задержки доставки. Агент проверяет статус заказа, историю перемещений и информацию перевозчика. Результаты влияют на дальнейший маршрут.

**Когда применять:** исследование нескольких источников, диагностика, неизвестная заранее последовательность действий, задачи, где промежуточные результаты меняют маршрут.

**Преимущества:** адаптивность, возможность остановиться при достаточности данных, гибкость в неизвестной среде.

**Ограничения:** дополнительные вызовы модели, рост задержки и стоимости; риск повторяющихся или бесконечных циклов; качество зависит от способности модели интерпретировать результаты инструментов.

**Обязательно предусмотреть:** максимальное число итераций, критерии завершения, обнаружение повторных вызовов, тайм-ауты, обработку ошибок и безопасную остановку.

В книге приведены варианты LangChain `ZERO_SHOT_REACT_DESCRIPTION` и `CHAT_ZERO_SHOT_REACT_DESCRIPTION`. Это названия типов агентов в конкретной версии экосистемы, а не универсальный современный стандарт. В новой реализации следует выбирать актуальный runtime/API, сохраняя сам принцип цикла ReAct.

## 2.3. Планировщик–исполнитель (Planner–Executor / Plan-and-Execute)

**Суть:** работа разделяется на две фазы. Планировщик формирует явный многошаговый план, исполнитель выполняет отдельные шаги инструментами.

**Как работает:**
1. Пользователь задаёт цель.
2. Планировщик формирует список подзадач.
3. План проверяется на полноту, зависимости и допустимость.
4. Исполнитель получает очередной шаг и нужный контекст.
5. Инструмент или исполнитель выполняет шаг.
6. Результат фиксируется в состоянии рабочего процесса.
7. Система переходит к следующему шагу либо корректирует план.
8. Результаты объединяются.

**Пример:** «Подготовь отчёт по просроченным счетам за месяц и отправь руководителю»: определить период → получить счета из ERP → проверить оплаты → сгруппировать задолженность → подготовить отчёт → показать пользователю → после подтверждения отправить.

**Когда применять:** сложные задачи с несколькими понятными этапами; процессы, где важны контроль, аудит и повторный запуск шага; длительные бизнес-процессы; ситуации, где план полезно показать или сохранить.

**Преимущества:** декомпозиция, прозрачность, удобная отладка, возможность использовать менее дорогую модель на простых шагах, а более сильную — для планирования.

**Ограничения:** план может устареть после новых данных; требуется перепланирование; отдельная фаза планирования добавляет задержку и может ошибиться.

**Практическая рекомендация:** не считать план неизменяемым. Разрешите пересматривать его при существенном изменении состояния, но ограничьте число перепланирований.

## 2.4. Агент декомпозиции запросов (Query-Decomposition / Self-Ask with Search)

**Суть:** сложный вопрос разбивается на более простые подвопросы. Для каждого агент получает подтверждающие данные, затем синтезирует ответ.

**Как работает:** определяет, почему вопрос нельзя решить одним шагом → формулирует подвопрос → получает ответ через поиск/БД/инструмент → определяет следующий подвопрос → повторяет до достаточности данных → объединяет результаты.

**Пример из логики книги:** чтобы сравнить продолжительность жизни двух людей, агент отдельно выясняет возраст первого и второго, а затем сравнивает результаты.

**Бизнес-пример:** «Какие клиенты принесли наибольшую выручку и одновременно увеличили задолженность?» Получить выручку → получить задолженность → нормализовать идентификаторы → сопоставить данные → рассчитать рейтинг.

**Когда применять:** составные вопросы, аналитика на основе внешних данных, сравнения, задачи, где каждый факт должен опираться на отдельный источник.

**Преимущества:** снижает риск пропустить часть вопроса; делает факты и промежуточные результаты явными.

**Ограничения:** много вызовов инструментов; возможны ошибки в выборе подвопросов; необходим контроль полноты и качества источников.

**Отличие от Planner–Executor:** декомпозиция строится вокруг последовательного уточнения вопроса и получения фактов. Planner–Executor сначала формирует более общий план действий, а затем исполняет его.

## 2.5. Агент с рефлексией и метарассуждениями (Reflection / Metareasoning)

**Суть:** агент не только выполняет шаги, но и проверяет свою работу относительно цели. Он ищет несоответствия, оценивает промежуточные результаты и при необходимости исправляет план.

**Цикл:** выполнить шаг → получить результат → сопоставить с ожидаемым состоянием/критериями → выявить ошибку или противоречие → принять результат, повторить шаг, сменить инструмент, перепланировать или передать человеку.

**Пример:** агент подготовил платёжное поручение. До отправки проверяет получателя, сумму, валюту, назначение и лимиты. Несовпадение блокирует операцию и вызывает запрос подтверждения.

**Когда применять:** критичные операции, процессы с высокой ценой ошибки, сложная диагностика, финансовые и иные чувствительные сценарии.

**Преимущества:** помогает обнаружить ошибки до распространения на следующие этапы; повышает контролируемость.

**Ограничения:** дополнительные вызовы и задержка; модель может неверно оценить собственный результат; самокритика не заменяет независимые проверки, бизнес-правила и тесты.

**Практический вывод:** критичные проверки лучше делать детерминированными правилами и независимыми валидаторами. LLM-рефлексия дополняет, но не заменяет их.

## 2.6. Агент глубокого исследования (Deep Research Agent)

**Суть:** многофазное исследование открытой задачи, для которой заранее неизвестны все необходимые источники, гипотезы и подзадачи.

**Типичный процесс:** сформировать стратегию → разбить темы на поисковые вопросы → обратиться к внешним источникам → оценить релевантность и надёжность → выявить пробелы и противоречия → уточнить гипотезы и повторить поиск → синтезировать выводы → проверить полноту.

**Пример:** исследование рынка перед запуском продукта: сегменты, конкуренты, цены, регулирование, тренды и риски.

**Когда применять:** открытые экспертные исследования, обзоры литературы, стратегический анализ, техническая экспертиза.

**Преимущества:** глубина, адаптивность, объединение нескольких методов — Planner–Executor, Query Decomposition, ReAct и Reflection.

**Ограничения:** высокая стоимость и задержка; зависимость от внешних источников; сложность оценки полноты; риск накопления ошибок.

**Важно:** Deep Research — не один алгоритм, а составная архитектура.

## 2.7. Сравнение архетипов

| Архетип | Адаптивность | Задержка/стоимость | Лучше всего подходит |
|---|---|---|---|
| Рефлекторный | Низкая | Очень низкие | Правила, триггеры, маршрутизация |
| ReAct | Высокая | Средние/высокие | Исследование, диагностика |
| Планировщик–исполнитель | Средняя/высокая | Средние/высокие | Многошаговые процессы |
| Декомпозиция запросов | Средняя | Средние/высокие | Составные фактические вопросы |
| Рефлексия | Высокая в проверке/коррекции | Высокие | Критичные задачи |
| Глубокое исследование | Очень высокая | Очень высокие | Длительные открытые исследования |


# 3. Стратегии выбора инструментов

Выбор инструмента — отдельная задача внутри оркестрации. В книге выделены три подхода.

## 3.1. Стандартный выбор (Standard Tool Selection)

**Принцип:** модели передают каталог доступных инструментов с названиями, описаниями и схемами параметров. Модель выбирает подходящий инструмент и формирует аргументы.

**Последовательность:** запрос → список инструментов → выбор моделию → формирование параметров → проверка → выполнение → возврат результата.

**Когда подходит:** небольшой или умеренный каталог; инструменты хорошо различаются; важна простота реализации.

**Плюсы:** легко реализовать, не нужна отдельная инфраструктура поиска.

**Минусы:** при большом каталоге описания конкурируют; модель может путать похожие функции; большой список увеличивает контекст.

**Как повысить точность:** короткое однозначное имя; описание назначения; типы, обязательность и диапазоны параметров; примеры вызова; описание того, чего инструмент не делает; тесты на похожие и неоднозначные запросы.

## 3.2. Семантический выбор (Semantic Tool Selection)

**Принцип:** описание каждого инструмента преобразуется в embedding и индексируется. Запрос также преобразуется в embedding. Поиск находит наиболее близкие инструменты, после чего модель выбирает и параметризует инструмент из сокращённого набора.

**Последовательность:** подготовить каталог → вычислить embedding описаний → сохранить векторный индекс → вычислить embedding запроса → найти Top-K → передать кандидатов модели → проверить аргументы → выполнить вызов.

**Когда подходит:** большой каталог, который трудно целиком передавать модели в каждом запросе.

**Плюсы:** сокращает список кандидатов и объём контекста; удобен для расширяемого каталога.

**Минусы:** семантические коллизии; похожие описания могут привести к неверному кандидату; качество зависит от embedding-модели, описаний и индекса.

**Что измерять:** recall@K (попал ли нужный инструмент в кандидаты), точность финального выбора, долю отказов, задержку поиска и стоимость.

## 3.3. Иерархический выбор (Hierarchical Tool Selection)

**Принцип:** выбор выполняется в два или более этапа. Сначала определяется категория инструментов, затем конкретная функция внутри неё.

**Пример групп:** вычисления, CRM, коммуникации, документы, финансы, аналитика.

**Последовательность:** классифицировать запрос по группе → загрузить инструменты группы → выбрать функцию → сформировать параметры → проверить и выполнить.

**Когда подходит:** очень большой каталог, много семантически похожих функций, естественное деление на бизнес-домены.

**Плюсы:** сужает область поиска; может повысить точность в сложном каталоге.

**Минусы:** дополнительные этапы и вызовы модели; ошибочная классификация группы может исключить нужный инструмент; группы требуют сопровождения.

**Практическое правило:** использовать, только когда каталог действительно велик и измерения показывают проблемы стандартного или семантического выбора.

## 3.4. Сравнение методов выбора инструментов

| Метод | Размер каталога | Задержка | Сложность | Основной риск |
|---|---|---|---|---|
| Стандартный | Малый/средний | Низкая/средняя | Низкая | Путаница между похожими функциями |
| Семантический | Средний/большой | Низкая на этапе поиска + вызов модели | Средняя | Нужный инструмент не попал в Top-K |
| Иерархический | Большой/очень большой | Обычно выше | Высокая | Ошибка выбора группы |

Не выбирайте семантический или иерархический поиск только потому, что они выглядят современнее. Сначала измерьте качество стандартного выбора на реальных запросах.

# 4. Исполнение инструментов: параметры, состояние и надёжность

Перед вызовом инструмента модель формирует параметры в соответствии со схемой. На вход могут влиять исходный запрос, текущее состояние агента, результаты предыдущих шагов, контекст пользователя, дата/время/местоположение (если действительно требуется), разрешённые значения и бизнес-правила.

Обязательные меры:
- проверка типов и обязательных полей;
- валидация диапазонов и допустимых значений;
- проверка прав пользователя и агента;
- тайм-ауты и ограниченные повторы;
- идемпотентность для повторяемых операций;
- обработка частичных отказов;
- журналирование вызова и результата;
- защита от повторного выполнения необратимого действия.

Не полагайтесь только на то, что модель правильно сформировала аргументы. Схема инструмента и программный валидатор должны проверить их до выполнения.

# 5. Топологии выполнения инструментов

Топология определяет, как инструменты связаны между собой и в каком порядке выполняются.

## 5.1. Выполнение одного инструмента (Single Tool)

**Схема:** запрос → выбор инструмента → параметры → вызов → ответ.

**Пример:** запросить погоду в городе и вернуть результат.

**Когда применять:** одна операция полностью решает задачу.

**Плюсы:** простота, низкая задержка, лёгкое тестирование.

**Ограничение:** не решает задачи, где нужны несколько источников или зависимые действия.

## 5.2. Параллельное выполнение (Parallel Tool Execution)

**Суть:** несколько независимых инструментов запускаются одновременно, результаты объединяются.

**Пример из книги:** обработка клиентского тикета. Одновременно запрашиваются карточка клиента, история заказов, журналы событий, похожие обращения и политика поддержки. Затем оркестратор объединяет результаты и формирует рекомендацию.

**Когда применять:** несколько источников можно опросить независимо; один результат не нужен для запуска другого.

**Плюсы:** сокращает суммарное ожидание по сравнению с последовательным выполнением; собирает более полную картину.

**Ограничения:** нагрузка на API, лимиты конкурентности, частичный отказ источника, противоречивые/устаревшие данные, гонки при изменении общего состояния.

**Предусмотреть:** лимит параллельности, индивидуальные тайм-ауты, частичные результаты, правила разрешения конфликтов и отмену ненужных задач.

## 5.3. Цепочки (Chains / Sequential Workflows)

**Суть:** действия выполняются последовательно; следующий шаг зависит от результата предыдущего.

**Пример:** найти клиента → получить договор → проверить условия → рассчитать скидку → подготовить предложение.

**Когда применять:** порядок известен, а результаты предыдущих этапов необходимы следующим.

**Плюсы:** понятная логика, простая трассировка, контролируемая последовательность.

**Ограничения:** общая задержка складывается из задержек этапов; ошибки могут накапливаться; длинная цепочка становится хрупкой.

**Рекомендация:** ограничивать длину цепочки, проверять промежуточные результаты и предусматривать восстановление с последнего успешного шага.

Книга показывает LangChain Expression Language (LCEL), где компоненты `Runnable` соединяются декларативно. Конкретный синтаксис и API меняются, но принцип последовательной композиции остаётся актуальным.

## 5.4. Графы (Graphs / State Graphs)

**Суть:** рабочий процесс представлен вершинами и рёбрами. Вершина — функция, вызов модели, инструмент или логический этап; ребро — допустимый переход.

Граф поддерживает условные переходы, ветвление, параллельные ветви, слияние результатов, циклы и повторные попытки, общую структуру состояния.

**Пример:** система поддержки классифицирует запрос, направляет его в ветку платежей или технической поддержки, выполняет нужный обработчик, затем сводит результаты в узле подготовки ответа.

**Когда применять:** много точек принятия решений; разные пути для классов запросов; ветвление и последующее объединение; сохранение состояния и восстановление долгих процессов; строгие правила переходов.

**Плюсы:** гибкость и явная структура; сложные процессы моделировать проще, чем длинными цепочками; удобны контрольные точки.

**Минусы:** сложнее проектировать и тестировать; чрезмерное ветвление увеличивает число путей; циклы, недостижимые узлы и конфликты состояния требуют проверки; может вырасти число вызовов модели.

**Практический вывод:** граф — не синоним «много агентов». Граф может управлять одним агентом, инструментами и обычными функциями. Он описывает структуру потока, а не количество LLM.

## 5.5. Сравнение топологий

| Топология | Зависимости | Ветвление | Параллельность | Сценарий |
|---|---|---|---|---|
| Один инструмент | Нет | Нет | Нет | Один поиск/расчёт |
| Параллельная | Независимые шаги | Ограничено | Да | Сбор данных из нескольких систем |
| Цепочка | Последовательные | Обычно нет | Обычно нет | Регламентированный процесс |
| Граф | Любые | Да | Да | Сложный процесс с разными маршрутами |

# 6. Контекст-инжиниринг (Context Engineering)

Контекст-инжиниринг — динамический выбор, структурирование и передача модели именно той информации, которая нужна на текущем шаге. Это шире, чем написание системного промпта.

## 6.1. Что может входить в контекст

- системные инструкции и роль агента;
- текущая цель пользователя;
- история диалога или её краткое резюме;
- результаты предыдущих инструментов;
- текущее состояние рабочего процесса;
- данные из памяти и баз знаний;
- политика компании и ограничения доступа;
- доступные инструменты и их схемы;
- результаты проверок и нерешённые вопросы.

## 6.2. Основные принципы

1. **Релевантность.** Передавать только то, что нужно для текущего шага.
2. **Структурированность.** Разделять инструкции, факты, состояние, результаты инструментов и пользовательские данные.
3. **Сжатие.** Длинную историю превращать в краткое резюме, сохраняя факты, ограничения и незавершённые действия.
4. **Актуальность.** Обновлять контекст после значимого шага.
5. **Контроль объёма.** Учитывать бюджет токенов, стоимость и задержку.
6. **Происхождение данных.** По возможности сохранять источник и время получения фактов.
7. **Изоляция недоверенного содержимого.** Внешние данные не должны переопределять системные инструкции.

## 6.3. Контекст на разных стадиях

| Стадия | Что передать модели |
|---|---|
| Планирование | Цель, ограничения, доступные возможности, релевантные знания |
| Выбор инструмента | Текущая подзадача, нужные схемы инструментов, результаты предыдущих шагов |
| Исполнение | Необходимые аргументы и состояние |
| Проверка | Ожидаемый и фактический результат, критерии качества |
| Итоговый ответ | Проверенные факты, ограничения, статус выполненных действий |

**Ключевая мысль книги:** оркестрация определяет, какие шаги делать; контекст-инжиниринг обеспечивает каждый шаг правильной информацией. Даже сильная модель работает плохо при нерелевантном или перегруженном контексте.


# 7. Дополнение: современные паттерны оркестрации (состояние на 05.11.2026)

Этот раздел расширяет классификацию книги современными практическими паттернами. Терминология фреймворков может отличаться: один подход может называться workflow, graph, supervisor, orchestrator-worker или agents-as-tools.

## 7.1. Детерминированный workflow / оркестрация кодом

Порядок шагов и переходы определяет код, а модель используется в конкретных точках: классификация, извлечение, генерация или оценка.

**Подходит:** повторяемые бизнес-процессы, SLA, строгие правила, финансовые и операционные действия.

**Преимущества:** предсказуемость, тестируемость, контроль стоимости и разрешённых переходов.

**Недостатки:** сложнее обрабатывать неожиданные сценарии без дополнительных ветвей.

**Выбор:** если процесс в основном известен заранее, код должен управлять потоком, а не отдавать модели полный контроль.

## 7.2. LLM-driven orchestration

Модель сама выбирает следующий шаг, инструмент или специалиста, исходя из задачи и наблюдений.

**Подходит:** открытые задачи, исследование, диагностика, непредсказуемая последовательность действий.

**Преимущества:** гибкость и адаптивность.

**Недостатки:** менее предсказуемые задержка, стоимость и поведение; требуются ограничения циклов, прав и ответственности.

**Выбор:** когда заранее прописать все возможные пути невозможно или слишком дорого.

## 7.3. Supervisor / Orchestrator–Workers

Центральный агент-координатор разбивает задачу на подзадачи, распределяет их между специализированными агентами/инструментами и объединяет результаты.

**Пример:** координатор поручает одному агенту изучить договор, второму — проверить платежи, третьему — сверить политику, затем объединяет выводы.

**Подходит:** несколько независимых областей экспертизы, параллельные подзадачи, единый итоговый ответ.

**Преимущества:** разделение ответственности, специализация, единая точка синтеза.

**Недостатки:** затраты на координацию, дублирование контекста, сложность согласования результатов.

## 7.4. Agents-as-Tools (агенты как инструменты)

Главный агент вызывает специализированного агента как ограниченную функцию. Специалист возвращает результат, но не забирает управление диалогом. Главный агент сохраняет ответственность за итоговый ответ.

**Когда выбирать:** специалист выполняет отдельную подзадачу — анализ документа, классификацию, расчёт, резюме.

**Отличие от handoff:** после подзадачи управление возвращается главному агенту.

## 7.5. Handoff / передача управления

Текущий агент передаёт управление специализированному агенту. Новый агент становится ответственным за дальнейшее выполнение или ответ.

**Когда выбирать:** для разных ветвей нужны разные инструкции, инструменты, политики или отдельная ответственность.

**Риски:** потеря контекста, циклические передачи, неясная ответственность за финальный ответ. Нужны условия передачи и правила возврата.

## 7.6. Evaluator–Optimizer / Critic loop

Один компонент генерирует результат, другой оценивает его по критериям и возвращает замечания. Генератор исправляет результат до прохождения порога или достижения лимита итераций.

**Подходит:** генерация отчётов, кода, аналитики и документов, где можно формализовать критерии качества.

**Не подходит:** если критерии субъективны или оценщик не способен независимо проверить результат.

**Обязательно:** критерии приёмки, лимит циклов, независимые тесты и fallback.

## 7.7. Group chat / совместное обсуждение

Несколько агентов обмениваются сообщениями в общей среде. Нужен механизм выбора следующего участника и завершения обсуждения.

**Подходит:** сценарии, где полезно сопоставить несколько точек зрения.

**Риски:** лишние токены, повторение аргументов, усиление общей ошибки, сложность завершения. Не использовать только ради имитации «команды экспертов».

## 7.8. Human-in-the-loop (человек в контуре)

На определённых шагах выполнение приостанавливается до подтверждения, уточнения или решения человека.

**Примеры:** подтверждение платежа; согласование отправки письма; утверждение изменения в CRM; проверка юридически значимого документа; разрешение на удаление данных.

**Практический принцип:** подтверждение требуется там, где действие имеет существенные последствия, необратимо или выходит за полномочия. Состояние процесса нужно сохранять, чтобы после ответа человека продолжить с нужного места.

## 7.9. Комбинированная оркестрация

Реальные системы часто сочетают несколько подходов:
- детерминированный граф задаёт контрольный каркас;
- LLM выбирает маршрут внутри ограниченной области;
- ReAct используется внутри исследовательской подзадачи;
- параллельные workers собирают независимые данные;
- evaluator проверяет итог;
- человек подтверждает критичное действие.

Это обычно практичнее, чем строить всю систему на одном универсальном паттерне.

# 8. Как выбрать архитектуру оркестрации: дерево решений

1. **Можно решить задачу одним вызовом модели без инструментов?** Да → обычный вызов модели.
2. **Действие надёжно определяется простым правилом?** Да → рефлекторная схема или детерминированный router.
3. **Нужен только один инструмент?** Да → single-tool workflow.
4. **Все источники независимы?** Да → параллельное выполнение и синтез.
5. **Порядок шагов заранее известен?** Да → цепочка или детерминированный workflow.
6. **Нужен план из нескольких проверяемых этапов?** Да → Planner–Executor.
7. **Следующий шаг зависит от результатов текущего действия?** Да → ReAct или динамический граф.
8. **Много условных ветвей, циклов и точек слияния?** Да → графовая оркестрация.
9. **Нужно распределять разные части задачи между специалистами?** Да → supervisor/workers, agents-as-tools или handoff — в зависимости от владельца финального ответа.
10. **Ошибка критична или действие необратимо?** Добавить независимую проверку, бизнес-правила и human approval. Не полагаться только на саморефлексию.
11. **Задача открытая и исследовательская?** Комбинировать планирование, декомпозицию, ReAct, оценку источников и синтез.

# 9. Актуальный чек-лист обследования будущего агента

Отмечайте каждый пункт как **Да / Нет / Частично / Неизвестно**. Неизвестные ответы — вопросы для уточнения концепции, а не повод автоматически выбирать сложную архитектуру.

## A. Характер задач

- [ ] Агент выполняет одну операцию или множество разных задач?
- [ ] Пользовательский запрос обычно однозначен?
- [ ] Нужно выполнять несколько действий для результата?
- [ ] Следующие шаги зависят от результатов предыдущих?
- [ ] Заранее известен порядок действий?
- [ ] Есть независимые действия для параллельного выполнения?
- [ ] Нужны поиск, сравнение и синтез данных из нескольких источников?
- [ ] Нужно исследовать неизвестную проблему и менять стратегию?
- [ ] Есть повторяющиеся регламентированные процессы?
- [ ] Задачи могут длиться минуты, часы или дни?

## B. Выбор и количество инструментов

- [ ] Сколько инструментов планируется на старте?
- [ ] Сколько инструментов ожидается после масштабирования?
- [ ] Есть инструменты с похожими названиями или назначением?
- [ ] Можно ли разделить инструменты на домены/группы?
- [ ] Достаточно ли описаний и схем для стандартного выбора?
- [ ] Нужен ли семантический поиск по каталогу?
- [ ] Нужен ли двухэтапный иерархический выбор?
- [ ] Нужно ли выбирать несколько инструментов для запроса?
- [ ] Должен ли агент отказываться от вызова, если подходящего инструмента нет?

## C. Динамика и адаптивность

- [ ] Может ли агент самостоятельно выбирать следующий шаг?
- [ ] Должен ли он строить план до исполнения?
- [ ] Нужно ли корректировать план после новых данных?
- [ ] Нужно ли возвращаться к предыдущим шагам?
- [ ] Нужны ли циклы проверки и исправления?
- [ ] Нужна ли декомпозиция сложных запросов на подвопросы?
- [ ] Нужно ли длительное исследование с несколькими итерациями поиска?

## D. Качество и критичность

- [ ] Какова цена ошибки?
- [ ] Есть ли необратимые действия?
- [ ] Нужна ли независимая проверка результата?
- [ ] Можно ли проверить результат программно?
- [ ] Нужна ли проверка фактов по нескольким источникам?
- [ ] Требуется ли аудит каждого шага?
- [ ] Нужно ли подтверждение человека перед отдельными действиями?
- [ ] Нужно ли сохранять промежуточные результаты и возобновлять процесс?

## E. Производительность

- [ ] Какое максимально допустимое время ответа?
- [ ] Допустимы ли несколько последовательных вызовов модели?
- [ ] Какой бюджет на один запрос/задачу?
- [ ] Есть ли лимиты API и внешних систем?
- [ ] Допустимы ли параллельные обращения?
- [ ] Есть ли длительные фоновые процессы?
- [ ] Нужны ли потоковая выдача, checkpoints и возобновление?

## F. Контекст и память

- [ ] Нужна ли история диалога?
- [ ] Нужна ли долговременная память между сессиями?
- [ ] Нужны ли документы, базы знаний или корпоративные данные?
- [ ] Должен ли контекст меняться на каждом этапе?
- [ ] Нужно ли передавать каждому исполнителю только часть контекста?
- [ ] Нужны ли резюме длинных историй и результатов?
- [ ] Нужно ли сохранять происхождение данных и временные метки?

## G. Несколько агентов или один

- [ ] Есть разные специализации, которые трудно объединить в одном агенте?
- [ ] Нужны разные системные инструкции или политики доступа?
- [ ] Есть независимые подзадачи для параллельных специалистов?
- [ ] Нужен единый координатор, который синтезирует результаты?
- [ ] Должен ли специалист напрямую общаться с пользователем?
- [ ] Можно ли решить задачу одним агентом с инструментами без потери качества?

**Правило:** мультиагентность оправдана, когда даёт измеримое преимущество — специализацию, изоляцию прав, параллелизм или управляемость. Увеличение числа агентов само по себе не является целью.


# 10. Матрица выбора метода оркестрации

| Если обнаружено в требованиях | Базовый кандидат | Что добавить |
|---|---|---|
| Простое правило или триггер | Рефлекторный / кодовый router | LLM-классификатор только для неоднозначных случаев |
| Один инструмент | Single-tool | Валидация параметров и результата |
| Независимые источники | Parallel execution | Слияние и обработка частичных отказов |
| Известный последовательный процесс | Chain / deterministic workflow | Checkpoints и retries |
| Много условных переходов | State graph | Явная схема состояния, тесты путей |
| Неизвестная последовательность действий | ReAct | Лимит циклов, stop conditions |
| Сложная цель с понятными этапами | Planner–Executor | Перепланирование и проверка плана |
| Составной фактический вопрос | Query decomposition | Проверка источников и полноты |
| Критичные действия | Workflow + независимая проверка | Human approval, аудит, компенсационные действия |
| Большое открытое исследование | Deep Research composition | Планирование + декомпозиция + ReAct + evaluator |
| Несколько экспертных областей | Supervisor / workers | Agents-as-tools или handoffs |
| Специалист должен владеть ответом | Handoff | Передача контекста и полномочий |
| Специалист выполняет подзадачу | Agents-as-tools | Единый координатор финального ответа |
| Результат нужно улучшать по критериям | Evaluator–Optimizer | Лимит итераций и независимые тесты |

# 11. Как выбрать не только оркестрацию, но и языковую модель

Вопрос «какая модель подойдёт лучше» нельзя решить только по названию или общему рейтингу. Модель нужно выбирать под конкретные роли в архитектуре и проверять на собственном наборе задач.

## 11.1. Разделите роли моделей

В одной системе могут использоваться разные модели.

| Роль | Что должна уметь модель |
|---|---|
| Router / классификатор | Надёжно определять тип запроса и выдавать структурированный маршрут |
| Planner | Декомпозировать цель, учитывать зависимости и ограничения |
| Tool caller | Корректно выбирать инструменты и заполнять аргументы |
| Worker / исполнитель | Выполнять узкую задачу с нужным контекстом |
| Researcher | Искать, сопоставлять, проверять и синтезировать источники |
| Evaluator / critic | Оценивать результат по критериям и выявлять ошибки |
| Final response | Формировать понятный и корректный ответ |

Не обязательно использовать одну и ту же самую сильную модель на всех ролях. Простую классификацию, извлечение полей и форматирование часто можно поручить компактной модели, если тесты подтверждают качество. Сложное планирование и неоднозначные решения могут требовать более сильной модели.

## 11.2. Критерии оценки модели

Оценивайте кандидатов на одинаковом наборе задач:

1. **Качество рассуждения и планирования** — полнота плана, корректные зависимости, отсутствие лишних шагов.
2. **Tool calling** — правильный выбор функции, точность аргументов, корректная обработка нескольких вызовов.
3. **Structured output** — соблюдение JSON Schema или другого формата.
4. **Instruction following** — соблюдение правил, ограничений и запретов.
5. **Устойчивость к неоднозначности** — способность запросить уточнение или отказаться от неподходящего действия.
6. **Работа с длинным контекстом** — нахождение релевантных данных без потери ограничений.
7. **Работа с ошибками инструментов** — корректное восстановление, смена стратегии или остановка.
8. **Качество синтеза** — отсутствие противоречий при объединении результатов.
9. **Калибровка уверенности** — корректное обозначение неопределённости.
10. **Задержка** — медиана и P95/P99 на реальных сценариях.
11. **Стоимость** — стоимость полного успешно выполненного процесса, а не одного вызова модели.
12. **Надёжность и доступность** — стабильность API, лимиты и корпоративные требования.

## 11.3. Метрики, которые стоит измерять

| Метрика | Что показывает |
|---|---|
| Task success rate | Доля задач с правильным результатом |
| Plan validity | Доля планов без пропущенных шагов и неверных зависимостей |
| Tool selection accuracy | Доля корректно выбранных инструментов |
| Argument validity | Доля вызовов с корректными параметрами |
| Tool execution success | Доля успешных вызовов инструментов |
| Recovery rate | Доля ошибок, после которых агент восстановился |
| Unsupported action rate | Частота запрещённых или необоснованных действий |
| Human escalation rate | Частота передачи человеку |
| Latency P50/P95/P99 | Типичное и хвостовое время выполнения |
| Cost per successful task | Полная стоимость одной успешно завершённой задачи |
| Context/token usage | Объём контекста и токенов на задачу |

Измеряйте стоимость на успешно выполненную задачу: дешёвая модель, которая часто ошибается и требует повторов, может оказаться дороже.

## 11.4. Практический протокол сравнения моделей

1. Сформировать 30–100 репрезентативных сценариев для первой итерации; для критичных систем расширить набор и включить редкие, ошибочные и adversarial-входы.
2. Для каждого сценария описать ожидаемый результат, допустимые действия и критерии прохождения.
3. Подготовить одинаковые инструменты, схемы, контекст и инструкции для всех кандидатов.
4. Запустить каждую модель на одном и том же наборе.
5. Сохранить трассировки: решения маршрутизатора, планы, tool calls, аргументы, ответы инструментов, повторы и финальный результат.
6. Оценить качество автоматически там, где возможно; критичные результаты дополнительно проверить человеком.
7. Измерить задержку и полную стоимость выполнения.
8. Повторить тесты на неоднозначных запросах, сбоях API, неполных данных и длинных цепочках.
9. Выбрать модель по порогам качества, безопасности, задержки и стоимости, а не по единому среднему баллу.
10. Оставить набор тестов как регрессионный benchmark.

## 11.6. Как выбирать размер/класс модели по роли

- **Небольшая быстрая модель:** классификация, маршрутизация по ограниченным категориям, извлечение полей, форматирование — если тесты подтверждают точность.
- **Модель среднего класса:** стандартный tool calling, типовые многошаговые процессы, структурированные планы ограниченной сложности.
- **Наиболее способная модель из кандидатов:** сложное планирование, неоднозначные задачи, исследование, синтез противоречивых данных, сложная диагностика.
- **Отдельный evaluator:** полезен, если критерии качества формализованы и оценщик способен проверять результат независимо. Его оценка не гарантирует правильность.

Часто оптимален маршрутизатор между моделями: простые шаги выполняет быстрая модель, сложные или рискованные эскалируются более сильной. Эту схему также нужно тестировать: маршрутизатор может ошибочно недооценить сложность задачи.

# 12. Чек-лист проектирования оркестрации перед разработкой

## Архитектура
- [ ] Определён минимальный рабочий сценарий агента.
- [ ] Выбран базовый паттерн и объяснено, почему он достаточен.
- [ ] Определено, какие участки детерминированы кодом, а какие управляются LLM.
- [ ] Определены условия перехода между этапами.
- [ ] Установлены лимиты итераций, глубины и параллельности.
- [ ] Определены условия завершения и эскалации.
- [ ] Решено, действительно ли нужны несколько агентов.

## Данные и контекст
- [ ] Описана схема состояния рабочего процесса.
- [ ] Определено, какие данные нужны каждому этапу.
- [ ] Настроено сжатие длинного контекста.
- [ ] Указаны источники данных и правила разрешения противоречий.
- [ ] Внешние данные отделены от доверенных системных инструкций.

## Инструменты
- [ ] Каталог инструментов и схемы документированы.
- [ ] Выбран стандартный, семантический или иерархический выбор.
- [ ] Аргументы проверяются до вызова.
- [ ] Есть тайм-ауты, retries, идемпотентность и обработка частичных отказов.
- [ ] Права инструментов соответствуют роли и задаче агента.

## Контроль и безопасность
- [ ] Критичные действия требуют подтверждения или независимой проверки.
- [ ] Результаты проверяются по формальным критериям там, где возможно.
- [ ] Есть аудит действий и трассировка шагов.
- [ ] Предусмотрено безопасное завершение при неопределённости.
- [ ] Можно восстановить или продолжить долгий процесс.

## Модель и оценка
- [ ] Сформирован benchmark реальных задач.
- [ ] Несколько моделей сравниваются на одинаковых условиях.
- [ ] Измеряется качество полного процесса, а не только ответ модели.
- [ ] Измеряются стоимость и задержка успешной задачи.
- [ ] Настроены регрессионные тесты и мониторинг качества.

# 14. Рекомендуемый результат для концепции агента

По итогам анализа главы и ответов на чек-лист стоит подготовить:
1. **Каталог сценариев:** задачи, входы, результаты и ограничения.
2. **Карту инструментов:** системы, функции, права, схемы параметров и владельцы.
3. **Карту оркестрации:** последовательность, параллельные ветви, условия, циклы и точки слияния.
4. **Модель состояния:** данные и статусы, передаваемые между шагами.
5. **Политику автономности:** что агент делает сам, где подтверждает, где эскалирует.
6. **Матрицу выбора моделей:** модель по ролям, критерии и результаты benchmark.
7. **План оценки:** тестовые сценарии, метрики качества, стоимости и задержки.
8. **План отказоустойчивости:** retries, fallback, остановка, восстановление и аудит.

# 15. Краткие выводы главы

- Оркестрация управляет не только инструментами, но и последовательностью действий, состоянием и контекстом.
- Рефлекторный подход подходит для простых правил; ReAct — для адаптивного цикла действий; Planner–Executor — для многошаговых задач с явным планом.
- Декомпозиция запросов полезна для составных фактических вопросов; рефлексия — для контроля ошибок; Deep Research объединяет методы для открытых исследований.
- Стандартный выбор инструментов проще; семантический помогает при большом каталоге; иерархический полезен при большом числе похожих функций.
- Один инструмент, параллельное выполнение, цепочки и графы — разные топологии, выбираемые по зависимостям и структуре задачи.
- Контекст-инжиниринг критичен: каждому шагу нужна релевантная, актуальная и структурированная информация.
- Современные системы сочетают кодовую оркестрацию и LLM-решения, используют supervisor/workers, handoffs, agents-as-tools и human-in-the-loop там, где это оправдано.
- Модель выбирают по тестам на собственных сценариях. Для разных ролей могут использоваться разные модели.
- Начинать следует с простейшего надёжного варианта и усложнять архитектуру только при измеримой необходимости.
