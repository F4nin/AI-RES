# AI RES — Информационная архитектура пользовательской документации

**Версия:** 1.1  
**Статус:** WORKING — структура и требования к документации; пользовательские инструкции ожидают реализации UI  
**Блок:** 16B  
**Основа:** Productization Plan v1.1, UX Concept v1.1, Architecture Concept v4.3  

## 1. Цель

Определить комплект пользовательской документации, аудитории, сценарии, структуру, правила достоверности и процедуру выпуска. Документ не является готовым User Guide: точные названия экранов, кнопок, статусы и скриншоты можно фиксировать только после реализации и acceptance соответствующей версии AI RES.

## 2. Аудитории и задачи

### 2.1. Бизнес-/системный аналитик

Пользователь должен уметь: создать рабочий контекст; добавить и проверить источники; сформулировать цель Epic; вести диалог с Manager; оценить и утвердить план; контролировать задачи и Worker Runs; анализировать/уточнять требования; просматривать evidence и provenance; создавать/проверять артефакты; управлять review, approval, baseline и change request; обрабатывать конфликты, ошибки и возвраты на доработку.

### 2.2. Стейкхолдер / владелец продукта

Пользователь должен уметь: просматривать статус и результаты Epic; читать требования и связанные доказательства; понимать риски, допущения, открытые вопросы и ограничения; оставлять review comments; принимать или отклонять решения в рамках своих полномочий; понимать, какие решения остаются за человеком.

### 2.3. Администратор организации / проекта

Пользователь должен уметь: управлять членством и ролями; понимать правила доступа; настраивать проектные правила в пределах полномочий; управлять подключениями и источниками; разбирать audit/operational notices в пределах предоставленной роли. Административное руководство выпускается отдельно, если соответствующий UI входит в релиз.

## 4. Обязательный шаблон описания пользовательского сценария

Для каждого сценария документация фиксирует:
1. Назначение и ожидаемый результат.
2. Предварительные условия и требуемую роль/permission.
3. Начальное состояние и входные данные.
4. Проверенные шаги в UI с фактическими названиями элементов.
5. Ожидаемое поведение и наблюдаемые статусы.
6. Варианты/ветвления и последствия решений.
7. Ошибки, блокировки и безопасное восстановление.
8. Что выполняет AI, что делает пользователь и что требует Human Approval.
9. Источники/артефакты, которые должны появиться в результате.
10. Версию продукта, на которой сценарий проверен.

## 5. Скриншоты и иллюстрации

- Скриншот делается только с релизной или явно обозначенной тестовой сборки.
- Для каждого изображения сохраняются build/version, дата, роль пользователя и сценарий.
- Не допускаются реальные персональные данные, секреты, коммерчески чувствительные данные и содержимое чужих проектов.
- Снимки проектных макетов нельзя выдавать за скриншоты работающего продукта.
- После существенного изменения UI проводится impact review всех затронутых изображений.

## 6. Контроль достоверности и публикации

1. Автор документации связывает каждый шаг с acceptance test / проверенным сценарием.
2. Product Owner подтверждает корректность пользовательского процесса и терминологии.
3. QA подтверждает, что описанное поведение присутствует в release build.
4. Security/Administrator reviewer проверяет описания полномочий, чувствительных операций и восстановления.
5. Accessibility/localization reviewer проверяет понятность и доступность.
6. Документация выпускается вместе с конкретным релизом и имеет собственный changelog.
7. Устаревшая инструкция помечается и заменяется; её нельзя молча оставлять в навигации как актуальную.

## 7. Терминология

Канонические термины берутся из `AI_RES_Glossary_v1.0.json` только после утверждения соответствующих записей. До approval документация может использовать согласованные проектные названия с пометкой, что терминология находится на review. UI labels не следует генерировать напрямую из непроверенного DRAFT glossary.

## 9. Release gate

Документ не может быть объявлен `PUBLISHED` до выполнения всех условий:
- соответствующий UI/workflow реализован и принят;
- каждый описанный шаг проверен на релизной сборке;
- отсутствуют инструкции, ведущие к недоступным или запрещённым действиям;
- screenshots очищены от чувствительных данных и привязаны к версии;
- glossary/labels согласованы;
- review по доступности и локализации завершён;
- указан product version и owner документа.
