# AI RES --- Жизненный цикл источников и изменений проектного контекста

**Версия:** 1.3\
**Статус:** BASELINED — source/context architecture and retrieval boundary; connector-specific limits and thresholds remain WORKING
**Область:** источники, версии, обработка, извлечение знаний, impact
assessment, обновление контекста и повторная проверка результатов.

## 1. Назначение и границы

Документ определяет, как AI RES принимает, хранит, обрабатывает и
обновляет проектные источники, а также оценивает влияние изменений
источников на требования, задачи, артефакты, Worker Results и Baseline.

Он дополняет `AI_RES_Source_Management_and_Analysis_v0.3.md`,
`AI_RES_Requirements_Lifecycle_v1.5.md`, `AI_RES_UX_Concept_v0.6.md` и
`AI_RES_MVP_Capability_Matrix_v1.6.md`. Не входит: полная реализация
коннекторов, окончательный выбор продуктов хранения, точные backend
enum, SLA, численные пороги и окончательная матрица форматов MVP.

## 2. Базовые принципы

1.  Оригинал источника сохраняется неизменяемо.
2.  Обновление создаёт новую версию, а не перезаписывает старую.
3.  Извлечённое утверждение, кандидат требования, требование, решение и
    артефакт --- разные сущности.
4.  Содержательные результаты имеют provenance либо явную маркировку
    вывода/гипотезы.
5.  Память и поисковые индексы не заменяют исходное хранилище.
6.  Индексация не равна пересмотру проектных решений.
7.  Изменение источника запускает оценку влияния, но не автоматическое
    изменение утверждённых объектов.
8.  Контекст Worker Run фиксирован и не меняется во время выполнения.
9.  Новые сведения используются в новых версиях Context Package.
10. Детерминированные правила имеют приоритет над семантической оценкой
    Manager.
11. Manager определяет содержательный маршрут; Workflow Engine исполняет
    переходы.
12. Policy & Permission Engine независимо проверяет права.
13. QA-переоценка обязательна для критических изменений.
14. Не перезапускается весь Epic, если достаточно точечной проверки.
15. Невозможность доказать влияние не означает отсутствие влияния:
    неопределённость фиксируется.

## 3. Доменная модель источников

  -----------------------------------------------------------------------
  Сущность                            Назначение
  ----------------------------------- -----------------------------------
  Source                              Логическая идентичность документа,
                                      репозитория, API или коннектора

  Source Version                      Неизменяемое состояние содержимого
                                      источника

  Source Fragment                     Страница, раздел, строка, endpoint,
                                      схема, файл или commit

  Extraction Record                   Результат извлечения из конкретной
                                      версии

  Source Assertion                    Утверждение, непосредственно
                                      присутствующее в источнике

  Derived Finding                     Вывод/интерпретация AI RES, не
                                      являющаяся буквальным утверждением

  Source Link                         Связь фрагмента/источника с
                                      проектными объектами

  Sync Event                          Событие получения/проверки
                                      обновления

  Change Set                          Набор изменений между двумя
                                      версиями

  Impact Assessment                   Оценка влияния Change Set

  Revalidation Action                 Проверка, повторный анализ или иное
                                      действие

  Context Package Version             Зафиксированный набор сведений для
                                      Worker Run
  -----------------------------------------------------------------------

### 3.1. Source и Source Version

`Source` описывает логическую идентичность и область применения
источника. `Source Version` --- конкретное неизменяемое состояние.

Рекомендуемые атрибуты Source: стабильный ID, название, тип, владелец
(если известен), проект/Epic, способ получения, внешний URI/ID,
классификация конфиденциальности, правила доступа, политика
синхронизации, авторитетность/назначение при наличии подтверждённых
правил.

Рекомендуемые атрибуты Source Version: ID версии, внешний маркер (commit
SHA, ETag и т.п.), content hash, время получения и время источника,
автор/инициатор (если известен), ссылка на оригинал,
формат/размер/encoding, результат security checks, статус извлечения,
версия parser/extractor, связь с предыдущей версией, provenance.

Hash помогает определить идентичность содержимого, но не доказывает
семантическую эквивалентность. Переименование/перемещение файла не
должно автоматически создавать новую логическую сущность или объединять
две сущности.

### 3.2. Разделение утверждения и интерпретации

Хранить отдельно исходный фрагмент, точное извлечённое утверждение,
нормализованное представление, вывод/гипотезу AI RES, кандидат
требования и последующее решение человека.

Пример: «Сервис должен отвечать не более чем за 2 секунды» --- Source
Assertion. Интерпретация «p95 при определённой нагрузке» --- Derived
Finding, если этого нет в источнике. Нормализованный кандидат требования
должен сохранить неопределённость, а не представить интерпретацию как
факт.

## 4. Категории источников и обработка

### 4.1. Документы и файлы

Для PDF, DOCX, Markdown, TXT, XLSX, CSV и изображений: 1. Проверить тип,
размер, целостность и безопасность. 2. Сохранить оригинал. 3. Извлечь
текст, таблицы и структуру. 4. Сохранить локаторы (страница, заголовок,
таблица, строка, абзац, область изображения --- если доступно). 5.
Создать Extraction Record. 6. Подготовить поисковые представления. 7.
Проверить качество извлечения. 8. Сделать источник доступным для анализа
с учётом ограничений.

OCR/мультимодальное понимание включать по обоснованным сценариям и
оценивать отдельно. Ошибка OCR не должна превращаться в уверенное
утверждение.

### 4.2. OpenAPI/Swagger

OpenAPI следует обрабатывать структурно, а не только как
YAML/JSON-текст. Извлекать paths/methods, operationId, parameters,
requestBody, response codes/schemas, components,
type/format/required/nullable, security schemes, servers, версии
спецификации и `$ref`.

Типы изменений: endpoint/method добавлен/удалён; параметр
добавлен/удалён/изменён; изменён тип, обязательность или формат; изменён
request/response; код ответа; схема безопасности; адрес/версия сервиса.

Не каждое изменение автоматически является breaking change.
Совместимость зависит от направления изменения, контракта, правил
версионирования и контекста потребителя.

### 4.3. GitHub/GitLab и репозитории

В MVP --- read-only в пределах подтверждённых scopes. Полезные единицы
анализа: commits/diff, файлы, конфигурации, OpenAPI/AsyncAPI, схемы и
миграции, тесты, README, pull/merge request metadata (если разрешено).

Код является свидетельством текущей реализации, но не автоматически
бизнес-намерения. Расхождение кода с утверждённым требованием
регистрируется как расхождение, а не автоматически исправляет
требование.

### 4.4. Внешние коннекторы

Для каждого коннектора задать поддерживаемые события,
polling/webhook/manual sync, частоту, API limits, retention/deletion,
модель прав, поведение при потере доступа и обработку повторных событий.
Webhook --- сигнал проверить/получить актуальную версию, а не
доказательство содержимого. Повторная доставка должна быть
идемпотентной.

## 5. Pipeline обработки

### 5.1. Приём и безопасность

1.  Проверить пользователя/сервис и полномочия.
2.  Проверить тип, размер, целостность и потенциально опасное
    содержимое.
3.  Для внешнего источника проверить scopes и целевой адрес.
4.  Сохранить оригинал или неизменяемый идентификатор внешней версии.
5.  Зафиксировать событие и audit record.
6.  Назначить Source/Source Version или предложить связь с существующим
    Source.

Содержимое источника --- недоверенные данные. Инструкции в документе,
коде, README или веб-странице не становятся системными инструкциями AI
RES и не могут менять роли, права, политики или конфигурацию.

### 5.2. Извлечение и нормализация

Определить формат и маршрут; извлечь текст/структуру/метаданные;
сохранить локаторы; определить неполноту; записать версию парсера;
сформировать Extraction Records.

Версия parser/extractor важна: результат может измениться при неизменном
оригинале. Extraction Record ссылается и на Source Version, и на версию
обработчика.

### 5.3. Индексация и retrieval

Рекомендуется гибридный поиск: - BM25/полнотекстовый --- точные
названия, идентификаторы, термины, пути, operationId; - semantic ---
смысловые совпадения и перефразирование; - структурные запросы ---
OpenAPI, таблицы, схемы, графовые отношения; - фильтры по правам,
проекту, Epic, версии и типу источника; - reranking --- только если
измерения показывают пользу.

В главе 6 книги RAG рассматривается как процесс retrieval + generation,
а Vector Store --- как компонент хранения/поиска векторов, не первичное
хранилище документов. Доступ фильтруется до передачи фрагментов модели.

### 5.4. Извлечение знаний

Различать Source Assertion, Candidate Requirement, Business Rule,
Constraint, Decision/Assumption, Risk, Open Question, Derived Finding и
Hypothesis.

Для каждого результата хранить source_version_id, fragment locator,
точный фрагмент/ссылку, метод извлечения, версию
обработчика/модели/конфигурации при необходимости, тип происхождения,
неопределённость и связи.

Гибридная регистрация кандидатов сохраняется: автоматическое создание
кандидата не является бизнес-утверждением требования.

## 6. Жизненный цикл Source Version

Рекомендуемые логические состояния (не окончательные backend enum):

  Состояние             Значение
  --------------------- ------------------------------------------------
  RECEIVED              Источник/обновление принято
  VALIDATING            Проверяются права, целостность и формат
  STORED                Оригинал/версия сохранены
  PROCESSING            Извлечение и подготовка
  AVAILABLE             Версия доступна для поиска/анализа
  PARTIALLY_AVAILABLE   Часть содержимого доступна, есть ограничения
  PROCESSING_FAILED     Обработка завершилась ошибкой
  SUPERSEDED            Появилась более новая версия; старая сохранена
  ARCHIVED              Источник выведен из активного использования
  ACCESS_REVOKED        Доступ отозван; чтение запрещено

Состояние источника не смешивать с состоянием impact assessment: Source
Version может быть AVAILABLE, пока анализ влияния ещё выполняется.

## 7. Сравнение версий и Change Set

### 7.1. База сравнения

Сравнивать с предыдущей успешно сохранённой версией того же Source; для
репозитория учитывать branch/commit/base commit; для API --- стабильный
ID и версию/ETag, если доступны. При ненадёжном сопоставлении не
выдавать автоматический семантический diff за точный.

### 7.2. Change Set

Содержит source_id, from/to version IDs, тип diff/алгоритм, изменения,
локаторы, полноту сравнения, неоднозначные соответствия, ссылки на
оригиналы, время/инициатора и версию алгоритма.

### 7.3. Классы diff

`ADDED`, `REMOVED`, `MODIFIED`, `MOVED`, `RESTRUCTURED`,
`METADATA_ONLY`, `UNKNOWN`.

Это типы изменения, а не уровни риска. Риск оценивается отдельно.

## 8. Impact Assessment

### 8.1. Гибридная архитектура

Используется ранее выбранная модель C: 1. Детерминированный слой
применяет обязательные правила, прямые traceability links, типы
объектов, политики и критические условия. 2. Manager оценивает
семантические последствия, непрямые связи и потребность в дополнительных
Workers. 3. Итоговая категория не может быть ниже категории,
установленной обязательным правилом.

Manager не может понизить критичность, установленную правилом. При
неполноте или конфликте оценки сохраняется более строгий безопасный
вариант и фиксируется неопределённость.

### 8.2. Категории

  -----------------------------------------------------------------------
  Категория               Смысл                   Действия
  ----------------------- ----------------------- -----------------------
  1\. Незначительное      Нет содержательного     Обновить
                          влияния на решения;     индекс/метаданные,
                          затронуты только        записать событие
                          поисковые/технические   
                          представления           

  2\. Требует проверки    Вероятно затронуты      Целевая проверка/QA;
                          связанные объекты,      Manager решает, нужен
                          критический риск не     ли новый Context
                          установлен              Package/Run

  3\. Критическое         Возможное влияние на    Обязательная
                          безопасность,           QA-переоценка,
                          архитектурные           блокировка затронутой
                          ограничения,            ветви при
                          обязательные контракты, необходимости, human
                          утверждённые решения,   escalation
                          Baseline или            
                          критические зависимости 
  -----------------------------------------------------------------------

Категория 3 не означает автоматический перезапуск исходного Worker. QA
может быть достаточно; Manager решает, требуется ли новая задача,
контекст и Run.

### 8.3. Объекты влияния

Source Assertions/Candidates; Requirements; Decisions/Assumptions/Risks;
Tasks/Plan Items; Artifacts; API/интеграционные контракты; модели
данных/диаграммы; тесты/критерии приёмки; Worker Results/Context
Packages; Baseline/Change Requests; известные downstream-потребители.

### 8.4. Сила связи

Указывать тип основания: прямой provenance; явная трассировка;
структурное соответствие; подтверждённая зависимость; семантическая
гипотеза; неизвестная/неполная связь. Семантическая гипотеза инициирует
проверку, но не отображается как доказанный факт.

### 8.5. Результат оценки

Impact Assessment содержит ID, Change Set, версии источника и правил,
время, затронутые объекты, основание/силу связи, категорию по объектам и
общую категорию, неопределённость, необходимые проверки, рекомендуемые и
фактические действия, решения человека, итоговый статус и аудит.

## 9. Влияние на Context Engineering

### 9.1. Память и контекст

По главе 6 книги: - Memory/Knowledge хранит источники, версии,
фрагменты, факты, историю, связи и индексы. - Context Engineering
выбирает и структурирует сведения для конкретного Worker сейчас.

Context Builder получает цель/ограничения от Manager; извлекает
релевантные объекты; проверяет актуальность и версии; применяет ACL;
включает обязательные сведения независимо от retrieval rank; формирует
компактный пакет с provenance и фиксирует его состав.

### 9.2. Неизменяемый Context Package

Каждый Worker Run использует фиксированную версию пакета. Рекомендуемый
состав: цель/границы; версия задачи/плана;
требования/решения/ограничения; Source Version и Fragment IDs;
допустимые результаты Workers; открытые вопросы/противоречия;
ограничения; tools/scopes; критерии и проверки; дата и версия Context
Builder; provenance manifest.

Пакет должен позволять восстановить, какие сведения получил Worker.

### 9.3. При обновлении источника

Активный Run продолжает работать со своим пакетом, если отдельное
критическое правило не требует остановки. Новые Run получают новую
версию пакета. Manager решает, какие задачи продолжать, приостановить
или повторить. Новый Run создаётся с новым Context Package Version и
ссылкой на предыдущую попытку.

## 10. Revalidation Plan и перепланирование

Manager может сформировать targeted review требования/артефакта;
повторное извлечение/анализ фрагментов; профильную проверку Worker;
независимый QA; повторный Worker Run; новую Task/Plan Version; Change
Request; human decision; отсутствие дальнейших действий с объяснением.

Для каждого действия фиксируются причина, объект, исполнитель, входные
версии, ожидаемый результат, критерии, зависимости, риск и необходимые
разрешения. Не создавать задачу ради каждого технического события. Task
нужна, когда требуется самостоятельная работа, результат или контрольная
точка.

## 11. Greenfield, Brownfield и Hybrid

**Greenfield:** источники описывают цели, контекст, ограничения,
нормативные условия и спецификации. Авторитетность источника и
утверждённые решения учитываются отдельно.

**Brownfield:** код/контракт/схема --- свидетельство текущей реализации,
не автоматически бизнес-намерение. Возможные расхождения: реализация vs
требование; документация vs реализация; реализация изменилась,
требование прежнее; требование изменилось решением владельца;
недостаточно данных.

**Hybrid:** явно хранить область `CURRENT_STATE`, `TARGET_STATE`,
`TRANSITION_STATE` либо эквивалент. Анализ не должен смешивать текущее и
целевое состояние.

## 12. Авторитетность, конфликты и свежесть

Нет универсального правила «последний документ главный». Авторитетность
определяется владельцем, формальным статусом, областью применимости,
датой действия, версией, правилами организации/проекта и типом факта
(бизнес-намерение, реализация, нормативное ограничение).

Рекомендуется отдельная Source Authority Policy, не равная retrieval
relevance. Manager может предложить изменение политики, но не менять её
самостоятельно.

При конфликте: сохранить обе позиции и provenance; определить
область/тип; применить формальные правила; оценить последствия;
автоматически разрешать только низкорисковый однозначный случай; иначе
предложить варианты уполномоченному лицу; сохранить решение, автора,
основание и срок действия.

Свежесть не равна авторитетности: старый утверждённый документ может
оставаться действующим, свежая заметка --- быть неутверждённой.

## 13. Безопасность и доверие

Least privilege; read-only по умолчанию для Brownfield; scopes для
коннекторов; проверка прав на каждую операцию; изоляция
организаций/проектов; секреты в Secrets Vault, не в LLM-контексте;
защита от prompt injection в
документах/коде/README/комментариях/веб-страницах; проверки файлов и
SSRF; сетевой доступ по политике.

Инструкции, найденные в источниках, остаются недоверенными данными.
Внешние изменяющие действия требуют отдельного разрешения/workflow.
Доступ к найденным фрагментам проверяется до формирования контекста.

## 14. UX и уведомления

По умолчанию показывать источник/версию, краткую сводку изменений,
затронутые объекты, выполненные проверки, ограничения и одно полезное
следующее действие. Не раскрывать техническую индексацию без запроса.

Группировать уведомления: решение, критический блокер, завершённая
существенная перепроверка, ошибка, информационное обновление. Не
показывать каждый chunk, embedding, API call или вызов Worker.
Отображать реальные события, не выдуманные проценты/ETA.

## 15. Ошибки и восстановление

Классы: источник/коннектор недоступен; права отозваны; частичная
выгрузка; неподдерживаемый формат; parser/OCR error; неоднозначная
версия; diff не построен; индекс не готов; retrieval неполон; impact не
завершён; Worker/QA failed; конфликт/блокер.

Сохранять оригинал и успешные результаты; повторять только идемпотентные
исправимые операции; ограничивать retries/backoff; не объявлять
частичный результат полным; не заменять отсутствующие данные догадкой;
независимым ветвям разрешать продолжение; Manager выбирает recovery,
Workflow Engine исполняет; после восстановления выполнять нужные
проверки.

## 16. Мониторинг и качество

Метрики: extraction success/partial/failure; качество OCR/структурного
извлечения на эталонах; точность локаторов/provenance; freshness и sync
lag; retrieval precision/recall; groundedness; полнота ACL-фильтрации;
качество diff и сопоставления версий; precision/recall impact detection;
пропущенные критические изменения; ложноположительные impact alerts;
время обнаружения/перепроверки; стоимость обработки; retries/recovery.

Тестировать end-to-end: source change → diff → impact → action selection
→ новый Context Package → результат проверки. Для критичных контрактов
--- regression-сценарии breaking/non-breaking changes.

## 17. Логические архитектурные компоненты

1.  Source Registry --- идентичность, владельцы, области, настройки.
2.  Source Storage/Version Store --- оригиналы и версии.
3.  Connector & Ingestion --- загрузка, sync, события, scopes.
4.  Extraction Pipeline --- парсеры, OCR, структурные экстракторы.
5.  Knowledge Indexing --- полнотекстовый/векторный/структурный индексы.
6.  Knowledge & Traceability Store --- утверждения, фрагменты, связи,
    provenance.
7.  Diff Engine --- сравнение и Change Set.
8.  Impact Assessment Service --- правила + семантическая оценка
    Manager.
9.  Context Builder --- сборка и фиксация Context Package.
10. Manager --- план анализа и revalidation actions.
11. Workflow Engine --- состояния, очереди, зависимости,
    retries/checkpoints.
12. Policy & Permission Engine --- независимая проверка доступа.

Это логические границы, не требование к отдельным микросервисам. На MVP
допустимо объединять компоненты при сохранении контрактов и

## 18. Рекомендуемый MVP

**Обязательно:** загрузка выбранных форматов; неизменяемое хранение
оригиналов/версий; метаданные/provenance; извлечение текста/структуры;
полнотекстовый и минимально необходимый semantic retrieval; Source
Assertion/Candidate Requirement; сравнение версий документов;
структурная обработка OpenAPI, если OpenAPI входит в MVP; traceability;
гибридный impact; фиксированный Context Package; targeted revalidation;
QA для критических изменений; аудит и ACL.

**Следующий этап:** GitHub/GitLab sync и commit-aware diff, если не
включены в исходный MVP; webhooks; глубокий анализ кода/миграций/тестов;
расширенный структурный diff; сложная политика авторитетности.

**Не внедрять заранее без обоснования:** GraphRAG для всех источников;
отдельную vector DB только ради embeddings; универсальное автоматическое
обновление всех документов; непрерывное сканирование репозиториев без
потребности; автоматическое переписывание Baseline.

# Дополнение v1.1. Внешние коннекторы и синхронизация источников

**Связанный документ:** `AI_RES_External_Integrations_and_Project_Context_v1.0.md`.

## 1. Уточнение модели Source

Source может поступать из ручной загрузки, локального/корпоративного хранилища или внешнего Connector. Для внешнего источника Source сохраняет provider, tenant/instance, external object type/ID, URL, owner, подключение, sync policy, ownership mode и classification. Source Version фиксирует provider version marker (commit SHA, ETag, revision ID или эквивалент), hash, observed_at, source_updated_at, sync_run_id и provenance.

External Object Mapping — отдельная связь, не замена Source/Source Version. Она позволяет связать внешний объект с Source и/или доменной сущностью AI RES. Mapping имеет статус PROPOSED/CONFIRMED/REJECTED/SUPERSEDED (предварительные значения), основание, источник сопоставления и версию правила.

## 2. Внешний ingestion pipeline

1. Connector Registry выбирает разрешённый адаптер и его версию.
2. Identity/Credential Broker предоставляет credential в runtime, не в модель.
3. Policy Engine проверяет пользователя/организацию/проект/объект/операцию.
4. Adapter получает внешний объект с cursor/version marker.
5. Проверяются tenant, schema, payload size, provenance и допустимость URL.
6. External Object Mapper разрешает mapping или создаёт кандидат.
7. Сохраняется Source Version или ссылка на неизменяемый внешний version marker.
8. Извлечение/нормализация/индексация выполняются существующим pipeline с ACL.
9. При изменении формируется Change Set и Impact Assessment.

## 3. Синхронизация

Рекомендуется сочетать webhook как сигнал, incremental polling для гарантии обнаружения пропусков, manual sync и reconciliation. Webhook валидируется и дедуплицируется; после него API используется для получения текущего состояния. Поддерживаются cursor/checkpoint, идемпотентность, защита от out-of-order events, rate limits, Retry-After, ограниченный backoff и partial sync.

## 4. Владение и конфликты

Source Authority Policy дополняется Ownership Policy по типу объекта/полю. Возможны EXTERNAL, AI_RES, SHARED и READ_ONLY_MIRROR; направления INBOUND, OUTBOUND и BIDIRECTIONAL. Нет глобального «последняя версия побеждает». Конфликт сохраняет обе версии, а неоднозначность создаёт Conflict/Pending Decision. Удаление снаружи фиксируется tombstone и проходит проверку зависимостей/retention.

## 5. Безопасность и эксплуатация

Read-only по умолчанию; минимальные scopes; секреты в Vault; повторная проверка прав при каждом вызове; ACL до retrieval; защита webhook/replay/SSRF/prompt injection; tenant isolation; аудит без credentials/payload secrets. Отзыв прав блокирует операции. При недоступности показывается последняя успешная версия и её дата; свежесть проверяется относительно задачи.

## 6. Границы MVP

Первая версия: read-only GitHub/GitLab для выбранных репозиториев, OpenAPI import, общий контракт адаптера, mapping, ручной/ограниченный polling, version markers, checkpoints, idempotency, ACL, audit, partial sync и impact pipeline. Jira/Confluence/SharePoint, расширенные webhooks и write/bidirectional sync — после MVP.

# Дополнение v1.2 — Knowledge & Memory retrieval baseline

Статус: BASELINED. Каноническое решение: PostgreSQL FTS + pgvector для MVP, MinIO для immutable originals, Redis только cache/ephemeral. Отдельные vector DB и GraphRAG отложены.

Обязательные правила: ACL до retrieval/rerank/context/cache/export; versioned parser/chunker/embedding/index generation; immutable ContextPackageVersion; provenance до fragment/offset; source ingestion и change impact остаются разными pipelines; ACL revocation invalidates cached access; reindex success не означает business revalidation. Требования к retrieval evaluation: Recall@k/Precision@k/MRR/nDCG где есть labels, citation correctness, stale rate, zero ACL leakage, latency and token cost.
